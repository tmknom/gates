# Security Considerations

GATES の導入を判断する人と運用者に向けて、利用者の側で守ることと、GATES が守るもの、残るリスクを示します。

GATES は、リスクをなくすのではなく、漏えいしたときの被害を小さくする仕組みです。
GitHub App Private Key をワークフローから離し、渡すトークンの対象、権限、期限を絞ります。
一方、トークンを受け取ったジョブの中と、GATES を動かす AWS アカウントの中には、GATES の制限が及びません。
その部分は、次の §1 のとおり利用者が守ります。

## 1. 利用者が守ること

### 1.1 インストール対象には、操作されてよいリポジトリだけを入れる

担当：GitHub App とオーナーの管理者

許可オーナーのワークフローは、どれもインストール対象のどのリポジトリに対しても、GitHub App の権限と発行上限の両方に含まれる権限を要求できます。
インストール対象は `Only select repositories` で選び、`All repositories` にしません。
リポジトリを加える前に、GitHub App に付与した権限で、許可オーナーのすべてのワークフローから操作されてよいかを検討します。
読み取りの権限だけなら、非公開のコードや誤ってコミットされた秘密情報を読まれてよいかが基準です。
書き込みの権限を付与しているなら、内容や設定を変えられ、削除されてもよいかも基準に加わります。

次のリポジトリは、インストール対象に含めません。
GATES 自身を書き換えるトークンを、許可オーナーのどのワークフローも要求できるようになるためです。

- GATES の Action と Terraform のコードを置くリポジトリ
- GATES の AWS リソースを変更できる IAM Role に信頼されたリポジトリ

許可オーナーが Organization なら、GitHub の既定では、リポジトリ管理者も自分のリポジトリをインストール対象に加えられます。
この設定を制限し、`installation_repositories:write` の権限を与える相手を管理します。

### 1.2 トークンを受け取るジョブで、信頼できないコードを動かさない

担当：ワークフロー利用者

トークンを受け取るジョブの中のコードは、どれもトークンを読み、トークンの権限で書き込みを含む操作ができます。
そのジョブは `id-token: write` を持つため、ジョブの中のコードは自分で GATES からトークンを受け取ることもできます。
そのトークンには、ワークフローが要求しなかった権限も、GitHub App の権限と発行上限の両方に含まれる範囲で含められます。
資格情報を守る境界はジョブです。

Pull Request のコードや、ほかのワークフローの成果物のような信頼できないコードは、トークンを受け取るジョブとは別のジョブで動かします。
**`pull_request_target` と `workflow_run` で起動するジョブは、fork からの Pull Request が起点でもトークンを受け取れます。**
GATES は起動イベントの種別で要求を拒否しないため、これらのジョブでは Pull Request の head のコードも、起点のワークフローの成果物も実行しません。

### 1.3 Action をコミットの SHA で参照する

担当：ワークフロー利用者

Action はタグやブランチではなく、運用者が示すコミットの SHA で参照します。
タグやブランチは、後から別のコミットを指すように変えられるためです。
Action のコンテナは root で動き、Runner の Docker のソケットを使える立場にあるため、改ざんされた Action を取り込むと被害が Runner 全体に及びます。

### 1.4 GitHub App の権限と発行上限を、必要な権限だけにする

担当：GitHub App とオーナーの管理者（GitHub App の権限）、運用者（発行上限）

**GitHub App に付与した権限のうち発行上限に含まれるものは、許可オーナーのすべてのワークフローに渡り得ます。**
GATES は、呼び出し元のワークフローによって発行できる権限を変えないためです。
許可オーナーのワークフローが必要とする権限を洗い出し、GitHub App の Repository permissions と発行上限の両方を、その範囲にします。
発行上限は、GitHub App に付与した権限を超えないようにし、権限名と水準の組で書きます。
各権限で使える API は、GitHub の [Permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps) で確かめます。

次の権限の `write` は影響が大きいため、自動化にどうしても要る場合に限って付与します。

- **`workflows`**：`contents:write` と組み合わせると、インストール対象のリポジトリのワークフローを書き換えられる。書き換えたワークフローは、ブランチと Environment の保護が止めない範囲で、そのリポジトリの Secrets と、そのリポジトリを信頼するクラウドの IAM Role などの権限を使える
- **`administration`**：リポジトリの設定の変更と削除、ブランチ保護と ruleset の変更、コラボレーターとデプロイキーの追加ができる。ブランチ保護と ruleset でリポジトリを守るなら、この権限を付与しない
- **`secrets`**：Secrets の値は読めないが、上書きと削除ができる
- **`actions`**：ワークフローの起動、実行ログの削除、OIDC JWT の `sub` のカスタマイズの変更ができる
- **`installation_repositories`**：インストール対象にリポジトリを加え、外せる
- **`repository_creation`**：リポジトリの作成とフォークの API を使える（ほかの権限も要る場合がある）

発行上限は、GitHub App の権限の誤りに備える手段です。
GitHub App の権限は GitHub の画面だけで変えられ、レビューを経ません。
発行上限は Terraform の変数のため、変更がレビューと Plan を経ます。
GitHub App に誤って広い権限を付与しても、発行上限に含まれない権限を GATES は発行しません。

**発行上限は、GATES を経ない署名には効きません。**
§1.5 のように KMS Key で署名されると、GitHub App の権限がそのまま上限になります。
そのため、発行上限を狭くしていても、GitHub App にも必要な権限だけを付与します。

Organization permissions、Account permissions、Enterprise permissions は付与しません。
GATES はこれらを発行しないため、付与しても使えません。
許可オーナーが Organization のとき、Organization permissions を付与すると、GATES を経ない署名で得られる権限が Organization の操作にまで広がります。

### 1.5 AWS で署名できる主体を絞る

担当：運用者

KMS Key で署名できることは、GitHub App として認証できることと同じです。
署名できれば、GATES の認可と発行上限を経ずに、GitHub App の権限の範囲でトークンを作れます。
GATES は Lambda のほかが署名できないように設定していますが、AWS アカウントで次の権限を持つ主体は、設定を書き換えて署名できます。

- KMS Key の Key Policy を書き換える権限（`kms:PutKeyPolicy`）
- Lambda の関数のコードや設定を更新する権限
- Lambda の実行 Role を別の関数に渡す権限（`iam:PassRole`）
- Lambda の実行 Role の引き受けの条件を書き換える権限（`iam:UpdateAssumeRolePolicy`）

これらは Terraform で GATES を適用する権限と重なるため、取り除けません。
Terraform を適用できる主体を絞り、変更をレビューします。
GATES は、不正な署名を検知して通知する仕組みを持ちません。

### 1.6 秘密鍵のコピーと KMS Key を守る

担当：運用者

- インポートの後、手元に秘密鍵のコピーを残さない。インポートのコマンドはダウンロードしたファイルを削除するが、バックアップなどに写ったものは消せない
- Terraform の Plan に KMS Key の削除が現れたら、適用しない。削除した KMS Key の鍵素材は戻らない

## 2. GATES が守るもの

- **秘密鍵を渡さない**：GitHub App Private Key は KMS から取り出せない。ワークフロー、Runner、Lambda のどれも秘密鍵を持たない
- **呼び出し元を確かめる**：OIDC JWT の署名と内容を確かめ、呼び出し元を不変 Owner ID で許可オーナーと照合する
- **要求を超えて発行しない**：対象は要求したリポジトリだけ、権限は要求した権限だけ（GitHub が加える `metadata:read` を除く）で、すべてのリポジトリを対象にする手段はない
- **許可しない権限を含む要求は全体を拒否する**：Repository permissions でない権限か、発行上限に含まれない権限を一つでも含む要求は、許可される権限だけに縮めずに拒否する
- **発行されたトークンを照合する**：GitHub が返したトークンの対象と権限が要求と合わなければ、返さずに失効を試みる
- **確かめられなければ返さない**：検証、認可、署名、照合のどれかが成り立たなければ、トークンを返さない
- **資格情報を記録しない**：秘密鍵、OIDC JWT、トークン、AWS の一時認証情報を、監査記録にもログにも書かない

## 3. 残るリスク

- **アクセスされる側のリポジトリは、自身への操作を GATES で制限できない**：GATES は呼び出し元とインストール対象の組み合わせを見ない。GitHub App の権限と発行上限が書き込みを含めば、許可オーナーのどのワークフローも、インストール対象のどのリポジトリでも書き換えられる。呼び出し元ごとに範囲を絞る認可は将来の候補である
- **インストール対象のリポジトリの Secrets とクラウドの権限に届き得る**：§1.4 の権限を付与すると、許可オーナーのワークフローが、ほかのリポジトリのワークフローを通して、そのリポジトリの Secrets や、そのリポジトリを信頼するクラウドの権限を使える
- **トークンで行われた変更は、トークンの失効の後も残る**：書き換えたコードとワークフロー、追加されたデプロイキー、Webhook、コラボレーターは、トークンの期限が短くても、ジョブの終了時に失効しても取り消されない
- **失効は確実ではない**：Action はジョブの終了時に失効を試みるが、失敗しても、Runner が強制終了されても、トークンは期限（発行から 1 時間）まで使える。そのあいだは、要求したリポジトリに、要求した権限の操作ができる
- **漏れた資格情報の再利用は防げない**：漏れた OIDC JWT と AWS の一時認証情報は、それぞれの期限のあいだ、ジョブの外から GATES を呼び出すのに使える可能性がある。同じ OIDC JWT の再利用の検出と、要求の回数の制限は、将来の候補である
- **Grant は Key Policy を戻しても残る**：Key Policy を書き換えられた主体は、KMS Key に自分の署名を許す Grant を作れる。疑いがあれば、`aws kms list-grants --key-id <KMS Key の ARN>` で Grant を確かめ、覚えのない Grant を `aws kms revoke-grant --key-id <KMS Key の ARN> --grant-id <Grant ID>` で取り消す

## 4. 監査で追えること

GATES は、Lambda まで届いた要求ごとに監査記録を残します。
監査記録には、結果と失敗の理由、呼び出し元のリポジトリ、ワークフロー実行の ID、起動イベント、要求したリポジトリと権限が入ります。
ワークフロー実行の ID から、GitHub のワークフロー実行にたどれます。
保持期間の既定は 7 日のため、監査の方針に合わせて延ばします。

GATES の監査記録で追えないものもあります。

- **IAM が拒否した呼び出し**：Lambda に届かないため、AWS CloudTrail で調べる。IAM Role の引き受けは既定で記録されるが、Lambda の呼び出しは CloudTrail のデータイベントの記録を有効にしたときだけ残る
- **`pull_request_target` と `workflow_run` の起点**：これらの記録の ref とコミットは既定のブランチの値で、起点の Pull Request やワークフロー実行を一つに特定できるとは限らない。起点は、ワークフロー実行の ID から GitHub をたどって調べる
- **トークンで行われた操作**：監査記録に残るのは、要求したリポジトリと権限、発行の結果までである。トークンでどの操作が行われたかは、GitHub 側の記録で調べる
