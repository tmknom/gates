# Security Considerations

GATES（GitHub App Token Exchange System）は、GitHub Actions のワークフローに、GitHub App Private Key を渡さずに、指定したリポジトリだけを対象にした短命なトークンを発行する仕組みです。
本文書は、GATES の導入を判断する人と **GATES 運用者**（GATES を AWS にデプロイして運用する人。以下、運用者）に向けて、GATES が守るもの、守らないもの、運用者、**ワークフロー利用者**（GATES からトークンを受け取るワークフローを書く人）、**GitHub App とオーナーの管理者**（GitHub App のインストール先と、オーナーの GitHub の設定を管理する人）が守る必要があるものを示します。

GATES は、リスクをなくすのではなく、影響を抑える仕組みです。
GitHub App の権限全体を使える GitHub App Private Key をワークフローから離し、ワークフローに渡すトークンの対象、権限、期限を絞ることで、トークンが漏れたときや悪用されたときの被害を小さくします。
そのため、トークンを受け取ったジョブの中や、GATES を動かす AWS アカウントの中には、GATES の制限が及ばない部分が残ります。
§2 から §5 はその部分を誰がどう守るかを、§6 は後から監査で追える範囲を示します。

## 1. GATES が守るもの

GATES の中心は、運用者の AWS アカウントで動く AWS Lambda の関数（以下、Lambda）と、GitHub App Private Key を保管する AWS KMS の鍵（KMS Key）です。
ワークフローは、GATES の Docker Action（以下、Action）を通じて Lambda を呼び出し、**Installation Access Token**（GitHub が GitHub App に発行する、対象と権限を限ったトークン。以下、トークン）を受け取ります。

GATES は次のことを守ります。

- **秘密鍵をどこにも渡さない**：GitHub App Private Key は KMS Key にインポートしてあり、KMS から取り出せない。トークンの発行に要る GitHub App JWT への署名は KMS の中で行うため、ワークフロー、Runner、Lambda のどれも秘密鍵を持たない。Lambda に許すのは KMS Key での署名だけで、鍵の管理や **鍵素材**（KMS Key にインポートした GitHub App Private Key の中身）の入れ替えはできない
- **呼び出し元を確かめる**：ワークフローは、自分がどのオーナーのどのリポジトリで動いているかを、GitHub が署名した OIDC JWT で示す。Lambda は認証なしでインターネットに公開された呼び出し口を持たず、呼び出しには、GATES の呼び出しだけを許された IAM Role の一時認証情報が要る。ワークフローは OIDC JWT を示してこの IAM Role を引き受け、AWS STS から一時認証情報を得る。引き受けられるのは、**許可オーナー**（GATES がトークンを発行してよいと運用者が設定した GitHub の Organization かユーザーアカウント）のワークフローだけである。Lambda はさらに OIDC JWT の署名と内容を確かめ、呼び出し元のオーナーを、名前ではなく変わらない ID（**不変 Owner ID**）で許可オーナーと照合する。このため、改名や、手放されたオーナー名の取得によって、許可オーナーになりすますことはできない
- **要求を超えて発行しない**：トークンの対象は要求で明示したリポジトリだけで、権限はリポジトリの内容を読む `contents:read` だけである（GitHub がリポジトリの基本情報を読む `metadata:read` を加えることがある）。全リポジトリを対象にする手段はなく、要求したリポジトリのうち一つでも許可されなければ、どのリポジトリのトークンも返さない
- **発行されたトークンを照合する**：GitHub が返したトークンの対象と権限を要求と照合し、合わなければワークフローに返さず、そのトークンの失効を試みる。失効が GitHub 側で成功することまでは保証しない
- **確かめられなければ返さない**：OIDC JWT の検証、認可、発行に使う Installation（GitHub App をオーナーにインストールした単位）の確認、署名、発行されたトークンの照合のどれかが成立しなければ、トークンを返さない（Fail Closed）。GitHub からの発行の応答が途中で失われた場合は、GitHub 側でトークンが発行されたかを確定できず、発行されていればそのトークンは有効期限まで有効なまま残り得る
- **資格情報を記録しない**：Lambda は要求ごとに監査記録を残すが、秘密鍵、OIDC JWT、GitHub App JWT、トークン、AWS 一時認証情報は、監査記録にもログにもエラー応答の本文にも書かない

## 2. 許可オーナーのワークフローが読めるリポジトリ

GATES は、呼び出し元を許可オーナー単位でしか区別しません。
許可オーナーのワークフローであれば、どのリポジトリのどのワークフローも、GitHub App の **インストール対象**（GitHub App をオーナーにインストールするときに選ぶ、GitHub App がアクセスできるリポジトリ）のどのリポジトリについても、トークンを得て読めます。
呼び出し元のリポジトリ、ワークフロー、チームごとにアクセス先を制限する認可は、現在はありません。

このため、どのリポジトリを読まれてよいかは、GATES の設定ではなくインストール対象で決まります。
インストール対象を `All repositories` にすると、オーナーのすべてのリポジトリが読める範囲に入るため、GitHub App とオーナーの管理者は `Only select repositories` で対象を選びます。
非公開のコードや設定、誤ってコミットされた秘密情報を含むような機密性の高いリポジトリは、インストール対象に加える前に、許可オーナーのすべてのワークフローから読まれてよいかを検討する必要があります。
インストール対象の変更は、GATES の設定を変えずに、以後の発行の要求に反映されます。
GATES はインストール対象を保持せず、発行のたびに GitHub が判定するためです。

許可オーナーが Organization の場合、Organization のオーナーのほかにも、インストール対象を変えられる人がいます。
GitHub の既定では、リポジトリ管理者が自分のリポジトリをインストール対象に加えられ、`installation_repositories:write` の権限で GitHub API を呼び出せる者も、リポジトリを対象に加えたり外したりできます。
GATES はこれらの設定を確かめないため、GitHub App とオーナーの管理者に当たる Organization のオーナーがリポジトリ管理者によるインストールを制限し、`installation_repositories:write` を与える相手を管理することを前提とします。

GitHub App の権限を広げても、GATES が発行するトークンの権限は広がりません。
GATES は発行のたびに `contents:read` だけを指定して要求し、返ったトークンの権限を照合するためです。
GATES の検証環境でも、GitHub App に Issues の権限を加え、Installation の側で承認した後に発行したトークンの権限は、`contents:read` と `metadata:read` のままでした。
ただし、KMS Key での署名を悪用されて GATES を経ずにトークンを作られた場合（§4）、そのトークンの権限の上限は GitHub App の権限になります。
GitHub App の権限を GATES が使う `Contents` の `Read-only` にとどめておけば、その場合に得られるトークンも読み取りの権限に限られます。

## 3. トークンを受け取るジョブの中のコード

GATES がトークンを渡す相手は、Action を置いたジョブです。
そのジョブの中のコードからトークンを守ることは、GATES にはできません。

まず、ジョブの中のステップとプロセスは、受け取ったトークンを読めます。
Action は、トークンを後続のステップに渡すため、また、ジョブの終了時に失効させるため、Runner の上のファイル（ステップの出力のファイルと、状態を保存するファイル）にトークンを書きます。
Runner はこれらのファイルをステップの後も消さず、GATES の検証環境では、同じジョブの後続のステップがそれを読めました。
前のステップが起動したバックグラウンドのプロセスも、Action のステップの最中にそのファイルを読めました。

次に、ジョブの中のコードは、自分で GATES からトークンを受け取れます。
OIDC JWT を要求するには、ワークフローかジョブの `permissions` で `id-token: write` を宣言する必要があり、Action を使うジョブは必ずこの権限を持ちます。
`id-token: write` を持つジョブでは、Action 以外のステップにも OIDC JWT の要求に使う値が渡るため、そのステップのコードも GATES からトークンを受け取れます。

つまり、資格情報を守る境界はジョブです。
ワークフロー利用者は、信頼できないコード（Pull Request のコード、ほかのワークフローの成果物など）とトークンを同じジョブに置かないことを、GATES を使う前提として守る必要があります。

この前提がとくに崩れやすいのが、`pull_request_target` と `workflow_run` で起動するジョブです。
どちらのジョブも、Pull Request の head や起点のワークフロー（`workflow_run` のジョブを起動したワークフロー）のファイルではなく、base のリポジトリの既定のブランチのワークフローで動きます。
そのうえで、Secrets を参照でき、宣言した `id-token: write` を持ちます。
GATES は、ワークフローを起動したイベントの種別で要求を拒否しません。
GATES の検証環境では、同じリポジトリのブランチからの Pull Request で起動した `pull_request_target` のジョブと、`workflow_run` のジョブが、どちらもトークンを受け取れました。
GitHub の公式資料によれば、fork からの Pull Request が起点でも Secrets と書き込みの権限を持つため、`id-token: write` も持つ見込みです（fork からの起動は確かめていません）。
そのジョブが Pull Request のコードや起点のワークフローの成果物を実行すると、そのコードがトークンを得られます。
GATES が IAM Role に設定する引き受けの条件（Trust Policy）は OIDC JWT の `sub`（呼び出し元を示す値）を見ており、`pull_request_target` のジョブの `sub` は `pull_request` のジョブと同じ形のため、この条件では 2 つを区別できません。

fork からの Pull Request で起動した `pull_request` のジョブは、GitHub の公式資料によれば、既定では書き込みの権限を読み取りに下げられるため、`id-token: write` を持ちません。
ただし、プライベートリポジトリで「Send write tokens to workflows from pull requests」を有効にすると持つ見込みです（確かめていません）。

ワークフローの書き方の規則（ジョブの分け方、トークンをジョブの外へ出さないこと、マスクの扱いなど）は、[Issue Token](../../.github/actions/issue-token/README.md) の「注意」にあります。

Action そのものも、ジョブの中で動くコードです。
Action のコンテナは root で動き、Runner はそこに Docker のソケットをマウントするため、Action のプログラムは Runner のホストの root に相当する権限を得られる立場にあります。
Action のプログラムはソケットを使いませんが、Action のプログラム、その依存、ビルド用のイメージが改ざんされると、この権限が悪用され得ます。
GATES は依存とビルド用のイメージをバージョンと digest で固定しており、ワークフロー利用者が Action をタグやブランチではなく commit SHA で参照することで、改ざんされたものを取り込む機会を抑えます。
なお、GitHub がホストする Linux の Runner では、同じジョブの `run` のステップもパスワードなしの `sudo` を使えるため、この権限は Action に固有のものではありません。

## 4. 運用者の AWS 権限が届く範囲

KMS Key で署名できることは、GitHub App として認証できることと同じです。
KMS Key で署名した GitHub App JWT があれば、GATES の認可を経ずにトークンを作れるため、§1 の呼び出し元の確認と、要求を超えて発行しない制限は効きません。
このとき得られるトークンの上限は、GitHub App の権限とインストール対象で決まります。

GATES は、KMS Key の **Key Policy**（KMS Key ごとに、誰がどの操作をできるかを定める設定）と IAM で、Lambda の **実行 Role**（Lambda が AWS の操作に使う IAM Role）のほかの主体が直接署名できないようにしています。
しかし、AWS アカウントで次の権限を持つ主体は、設定を書き換えることで署名できます。

- **Key Policy を書き換える権限**（`kms:PutKeyPolicy`）：自分に署名を許可できる。Key Policy で一時的に Grant（Key Policy とは別に KMS Key の操作を許可する仕組み）の作成を許可して作った Grant は、Key Policy を元に戻しても残る
- **Lambda の関数を更新する権限**：関数のコードや設定を変えて、実行 Role の権限で署名させられる。実行 Role を別の関数に渡す権限（`iam:PassRole`）でも同じことができる
- **実行 Role の Trust Policy を書き換える権限**（`iam:UpdateAssumeRolePolicy`）：実行 Role を引き受けて署名できる

これらの権限は、Terraform で GATES を適用するのに要る権限と重なるため、適用する主体から取り除けません。
たとえば `kms:PutKeyPolicy` を Key Policy から外すと Terraform で Key Policy を更新できなくなり、署名を拒む `Deny` を加えても、同じ権限で消せます。
このため、Terraform を適用できる主体を絞り、変更をレビューすることが運用者の責任になります。
GATES は、Terraform を運用者の手元から適用し、CI には適用の権限を与えない構成をとっています。

Lambda のコードの脆弱性などで実行 Role の権限を奪われた場合も、同じように署名を悪用されます。
KMS は秘密鍵の取り出しを防ぎますが、署名の能力の悪用は防ぎません。

ほかにも、設定では強制できず、運用者が守るものがあります。

- **インポート前の秘密鍵のコピー**：KMS Key にインポートした後、手元のコピーを削除する
- **鍵素材のインポートの権限**：Key Policy は、インポートする主体と Terraform を適用する主体を区別しない。両者を分けたいときは、IAM で権限を別の主体に割り当てる
- **Plan に現れた KMS Key の削除**：Terraform の設定で削除を防いでいるが、KMS Key のリソースの設定そのものを取り除いた場合の削除は防げない。Plan に KMS Key の削除が現れたら、適用を止める

GATES は、不正な変更や署名を検知して通知する仕組みを持たないため、悪用に気付くまでの時間は保証できません。
悪用が判明したときは、GitHub 側で GitHub App Private Key を削除して失効させます。
KMS Key を無効にしても署名は止まりますが、KMS Key を有効に戻す権限を持つ主体が元に戻せるため、それだけでは確実に止められません。

## 5. トークンの寿命と失効

トークンの有効期限は発行から 1 時間で、GitHub が決め、GATES は延長しません。
Action は、ジョブの終了時に、後続のステップが失敗した場合やジョブがキャンセルされた場合も含めて、トークンの失効を試みます。
Action がトークンを受け取った後、後続のステップに渡す前に失敗した場合は、その時点で失効を試みます。

この失効は確実ではありません。
失効の要求が失敗した場合や、失効を試みる前に Runner がコンテナを強制終了するか Runner そのものが止まった場合、トークンは有効期限まで使えるまま残ります。
失効に失敗しても、Action はジョブを失敗させず、警告の注釈を残すだけです。
残ったトークンの対象と権限は、§1 のとおり要求した範囲に限られます。

失効の要求が成功した後も、短い間はトークンが使えることがあります。
GitHub は、失効が効くまでの時間を公開していません。
その間にトークンを使えるのは同じジョブのステップとプロセスで、それらは失効の前からトークンを読めるため、§3 の前提のもとでは新たなリスクにはなりません。

トークンに限らず、OIDC JWT や AWS 一時認証情報が漏れて再利用されることも、GATES は完全には防ぎません。
たとえば、漏れた AWS 一時認証情報と GATES 用の OIDC JWT は、それぞれの有効期限の間、元のジョブの外から Lambda を呼び出すのに使える可能性があります。
有効期限内に同じ OIDC JWT を使った要求の検出と、連続した要求の制限は、将来取り込む候補で、現在はありません。
漏えいの影響は、トークンの対象、権限、期限と、インストール対象の範囲にとどまります（§2）。

## 6. 監査で追えることと追えないこと

Lambda は、要求ごとに監査記録を CloudWatch Logs に残します。
監査記録には、処理の結果（成功か、失敗の種類）と拒否の理由、呼び出したリポジトリ、ワークフロー実行の ID とその試行の番号、起動したイベント、ref、ワークフロー、行為者などの起動の属性、要求したリポジトリと権限が入ります。
ただし、呼び出し元を確かめる前に失敗した要求では、確かめていない値を呼び出し元として記録しません。
ワークフロー実行の ID から、GitHub 上のワークフロー実行にたどれます。

GATES の応答には、成功と失敗のどちらにも、監査記録と突き合わせるための `request_id` が付きます。
GATES が要求を拒否したか発行に失敗したときは、Action が失敗の注釈に `request_id` を書くため、ワークフロー利用者は `request_id` を運用者に伝え、運用者はそれで監査記録を探せます。
GATES の想定外の失敗では応答に `request_id` がないため、ワークフロー利用者はワークフローの実行を運用者に伝えます。
監査記録の保持期間は Terraform の入力で決まり、既定は 7 日です。
監査に求める期間は組織の方針によって異なるため、運用者が自組織の方針に合わせて設定します。

GATES の監査記録は、Lambda まで届いた要求だけを残します。
IAM が拒否した呼び出しは Lambda まで届かないため、GATES の記録には残りません。
これらの記録は AWS の CloudTrail が担います。
IAM Role の引き受けは CloudTrail の管理イベントで、拒否された引き受けも既定で残ります。
一方、Lambda の呼び出しは CloudTrail のデータイベントで、データイベントの記録を有効にしていなければ、成功も拒否も残りません。

`pull_request_target` と `workflow_run` で起動したジョブの監査記録からは、§3 の危険の起点を特定できないことがあります。
どちらの記録でも、ref と commit は既定のブランチの値になります。
`workflow_run` の記録には、起点のワークフロー実行を示す項目がありません。
`pull_request_target` の記録には Pull Request の head のブランチ名が残りますが、Pull Request の番号、fork の持ち主、head の commit を含まないため、Pull Request を一つに特定できるとは限りません。
起点は、記録のワークフロー実行の ID から GitHub のワークフロー実行をたどって調べます。
GitHub 側の記録の保持期間を過ぎるか記録が削除されると、起点は調べられなくなります。

## 7. さらに読む

本文書の根拠と、本文書が扱わなかった内部の設計は、次の文書にあります。

- [Security Design](../design/security.md)：信頼境界ごとに保証することとしないこと、認可の条件、資格情報の扱い、受容するリスクとその理由。Issuer の公開鍵の保持期間や JWKS の再取得の上限のような、GATES の内部の扱いに関わるリスクと、それに運用者が対応する方法も含む
- [Requirements](../spec/requirements.md)：Fail Closed（QR-003）、秘密情報の保護（QR-004）、秘密鍵の保護（QR-008）などの要求と、Requirements の §2 にある役割ごとの責任
- [Scope](../spec/scope.md)：細粒度の認可、OIDC JWT の再利用の検出、レート制限など、将来取り込む候補の機能と、対象外とする範囲
- [Formal Models](../../formal/README.md)：認可と発行処理の規則を Alloy で、OIDC JWT の Claim の受理条件を Z3 で、指定した範囲で検証したモデル。どちらのモデルも Go の実装との一致は確かめておらず、それはテストが担う。GitHub のふるまいは Alloy のモデルの対象外である
