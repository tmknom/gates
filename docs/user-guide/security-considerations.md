# Security Considerations

GATES の導入を判断する人と運用者に向けて、利用者の側で守ることと、GATES が守るもの、残るリスクを示します。

GATES は、リスクをなくすのではなく、漏えいしたときの被害を小さくする仕組みです。
GitHub App Private Key をワークフローから離し、渡すトークンの対象、権限、期限を絞ります。
一方、トークンを受け取ったジョブの中と、GATES を動かす AWS アカウントの中には、GATES の制限が及びません。
その部分は、利用者が守ります。

## 1. 利用者が守ること

### 1.1 インストール対象には、操作されてよいリポジトリだけを入れる

担当：GitHub App とオーナーの管理者

リポジトリポリシーを適用しないデプロイでは、許可オーナーのワークフローは、どれもインストール対象のうち保護対象でないリポジトリに対して、GitHub App に付与され、発行上限が許す権限を要求できます。
適用するデプロイでも、リポジトリポリシーで広く許すか、書き込みのトークンで書き換えられると、許される Caller と権限が広がり得ます。
インストール対象は `Only select repositories` で選び、`All repositories` にしません。
リポジトリを加える前に、GitHub App に付与した権限で、許可オーナーのすべてのワークフローから操作されてよいかを検討します。
リポジトリポリシーを適用するデプロイでは、そのリポジトリのリポジトリポリシーで許すワークフローから操作されてよいかを基準にします。
読み取りの権限だけなら、非公開のコードや誤ってコミットされた秘密情報を読まれてよいかが基準です。
書き込みの権限を付与しているなら、内容や設定を変えられ、削除されてもよいかも基準に加わります。
操作できるワークフローを一部のリポジトリのものに限りたいリポジトリは、加える前に運用者が保護対象にします。

次のリポジトリは、保護対象にするかどうかにかかわらず、インストール対象に含めません。
GATES 自身を書き換えるトークンを、許可オーナーのワークフローが要求できるようになるためです。

- GATES の Action と Terraform のコードを置くリポジトリ
- GATES の AWS リソースを変更できる IAM Role に信頼されたリポジトリ

許可オーナーが Organization なら、GitHub の既定では、リポジトリ管理者も自分のリポジトリをインストール対象に加えられます。
この設定を制限し、`installation_repositories:write` の権限を与える相手を管理します。

### 1.2 守りたいリポジトリを保護対象にする

担当：運用者

インストール対象のうち、操作できるワークフローを一部のリポジトリのものに限りたいリポジトリを、保護対象の一覧に加えます。
Secrets を持つリポジトリや、クラウドの IAM Role などに信頼されたリポジトリも、ほかのワークフローから書き換えられると Secrets と外部の権限に届くため、保護対象の候補です。

- **リポジトリポリシーを適用しないデプロイでは、新しいリポジトリは一覧に加えるまで保護されない**：一覧にないリポジトリは、インストール対象に加えた時点から、許可オーナーのどのワークフローも要求できる。守りたいリポジトリは、一覧に加えて Terraform で適用してから、インストール対象に加える
- **リポジトリポリシーを適用するデプロイでは、一覧がリポジトリポリシーの書き換えに対する上限になる**：リポジトリポリシーは既定ブランチに書き込める人と、`contents:write` か `administration:write` を許された Caller が書き換えられる。その書き換えでも越えさせたくない Caller と権限の上限は、一覧で決める。保護対象にも、そのリポジトリのリポジトリポリシーが要る
- **許可 Caller のリポジトリも守る**：許可 Caller のリポジトリがインストール対象に含まれ、保護対象でないと、許可オーナーのどのワークフローも、`contents:write` と `workflows:write` のトークンでそのリポジトリのワークフローを書き換え、許可 Caller として保護対象を要求できる。GitHub App の権限と発行上限が書き込みを含むなら、許可 Caller のリポジトリも保護対象にするか、インストール対象から外す
- **ID と名前は REST API で調べて書く**：保護対象と許可 Caller は、Repository ID と名前の組で書く。書き誤った許可 Caller はどの Caller にも当たらず、書き誤った保護対象への発行は止まる。どちらも拒否に倒れるが、正しい要求も通らなくなる
- **改名したら一覧を直す**：保護対象を改名すると、一覧の名前を直すまで、その保護対象への発行が止まる。許可 Caller のリポジトリを改名すると、直すまで、そのリポジトリからの保護対象への要求が拒否される。どちらも保護は外れない

### 1.3 リポジトリポリシーで許す Caller と権限を絞る

担当：リポジトリの管理者

リポジトリポリシーを適用するデプロイでは、リポジトリポリシーで許した Caller のワークフローが、許した権限でそのリポジトリを操作できます。
書き方は [Repository Policy](repository-policy.md) にあります。

- **`contents:write` と `administration:write` は、すべてを許すことと同じ**：これらを許した Caller は、トークンでリポジトリポリシーを書き換え、自分にほかの権限を許せる。GitHub App の権限と発行上限の範囲で、そのリポジトリへのすべての権限を許すものとして判断する
- **既定ブランチに書き込める人を絞る**：既定ブランチに書き込めるだれもが、リポジトリポリシーを変えられる。ブランチ保護、Rulesets、CODEOWNERS で変更にレビューを求めるか、書き込める人を絞る。これらの機能は、プランとリポジトリの公開範囲によって使えないことがある
- **`.github/gates-policy.yml` をシンボリックリンクにしない**：リンク先がファイルなら、その内容がリポジトリポリシーとして読まれ、リンク先を書き換えられる人もリポジトリポリシーを変えられる
- **複製したリポジトリポリシーを確かめる**：テンプレートなどから内容を複製して作ったリポジトリは、複製元と同じ Caller と権限を許す
- **Caller のリポジトリの改名と作り直しのたびに直す**：直すまで、その Caller の要求は拒否される

### 1.4 トークンを受け取るジョブで、信頼できないコードを動かさない

担当：ワークフロー利用者

トークンを受け取るジョブの中のコードは、どれもトークンを読み、トークンの権限で書き込みを含む操作ができます。
そのジョブは `id-token: write` を持つため、ジョブの中のコードは自分で GATES からトークンを受け取ることもできます。
そのトークンには、ワークフローが要求しなかった権限も、GitHub App の権限と発行上限が許す範囲で含められます。
ジョブのリポジトリが許可 Caller のリポジトリなら、ブランチ、イベント、ワークフローによらず、その権限の上限の範囲で保護対象にも届きます。
資格情報を守る境界はジョブです。

Pull Request のコードや、ほかのワークフローの成果物のような信頼できないコードは、トークンを受け取るジョブとは別のジョブで動かします。
**`pull_request_target` と `workflow_run` で起動するジョブは、fork からの Pull Request が起点でもトークンを受け取れます。**
GATES は起動イベントの種別で要求を拒否しないため、これらのジョブでは Pull Request の head のコードも、起点のワークフローの成果物も実行しません。

### 1.5 Action をコミットの SHA で参照する

担当：ワークフロー利用者

Action はタグやブランチではなく、運用者が示すコミットの SHA で参照します。
タグやブランチは、後から別のコミットを指すように変えられるためです。
Action のコンテナは root で動き、Runner の Docker のソケットを使える立場にあるため、改ざんされた Action を取り込むと被害が Runner 全体に及びます。

### 1.6 GitHub App の権限、発行上限、権限の上限を、必要な権限だけにする

担当：GitHub App とオーナーの管理者（GitHub App の権限）、運用者（発行上限と権限の上限）

**GitHub App に付与した権限のうち発行上限が許すものは、保護対象でないリポジトリに対して、許可オーナーのすべてのワークフローに渡り得ます。**
発行上限は、どの Caller にも同じ権限を許すためです。
許可オーナーのワークフローが必要とする権限を洗い出し、GitHub App の Repository permissions と発行上限の両方を、その範囲にします。
発行上限は、GitHub App に付与した権限を超えないようにし、権限名と水準の組で書きます。
各権限で使える API は、GitHub の [Permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps) で確かめます。

**発行上限と権限の上限には、権限名ごとに、必要な最も低い水準を書きます。**
`write` を書くと、同じ権限名の `read` の要求も許します。
読み取りだけで足りる権限に `write` を書くと、その権限の書き込みも要求できるようになります。
許可 Caller の権限の上限に `metadata` を書かなくても、保護対象のトークンには、GitHub が加える `metadata:read` が含まれることがあります。

次の権限の `write` は影響が大きいため、自動化にどうしても要る場合に限って付与します。

- **`workflows`**：`contents:write` と組み合わせると、インストール対象のリポジトリのワークフローを書き換えられる。書き換えたワークフローは、ブランチと Environment の保護が止めない範囲で、そのリポジトリの Secrets と、そのリポジトリを信頼するクラウドの IAM Role などの権限を使える
- **`administration`**：リポジトリの設定の変更と削除、ブランチ保護と ruleset の変更、コラボレーターとデプロイキーの追加ができる。ブランチ保護と ruleset でリポジトリを守るなら、この権限を付与しない
- **`secrets`**：Secrets の値は読めないが、上書きと削除ができる
- **`actions`**：ワークフローの起動、実行ログの削除、OIDC JWT の `sub` のカスタマイズの変更ができる
- **`installation_repositories`**：インストール対象にリポジトリを加え、外せる
- **`repository_creation`**：リポジトリの作成とフォークの API を使える（ほかの権限も要る場合がある）

発行上限は、GitHub App の権限の誤りに備える手段です。
GitHub App の権限は GitHub の画面だけで変えられ、レビューを経ません。
発行上限は Terraform の変数のため、変更がレビューと Plan を経ます。
GitHub App に誤って広い権限を付与しても、発行上限が許さない権限を GATES は発行しません。

**発行上限は、GATES を経ない署名には効きません。**
KMS Key で署名されると、GitHub App の権限がそのまま上限になります。
そのため、発行上限を狭くしていても、GitHub App にも必要な権限だけを付与します。

リポジトリポリシーを適用するデプロイでは、GATES がリポジトリポリシーを読むために、`Single file` を `Read-only` で付与し、パスを `.github/gates-policy.yml` だけにします。
`Read and write` にすると、`single_file:write` のトークンでリポジトリポリシーを書き換えられ得るため、付与しません。
パスを加えると、同じ署名で読めるファイルが増えるため、加えません。
GATES は `Single file` の権限で読むため、`Contents` の `Read-only` では代わりになりません。

Organization permissions、Account permissions、Enterprise permissions は付与しません。
GATES はこれらを発行しないため、付与しても使えません。
許可オーナーが Organization のとき、Organization permissions を付与すると、GATES を経ない署名で得られる権限が Organization の操作にまで広がります。

### 1.7 AWS で署名できる主体を絞る

担当：運用者

KMS Key で署名できることは、GitHub App として認証できることと同じです。
署名できれば、GATES の認可、発行上限、保護対象の一覧を経ずに、GitHub App の権限の範囲でトークンを作れます。
GATES は Lambda のほかが署名できないように設定していますが、AWS アカウントで次の権限を持つ主体は、設定を書き換えて署名できます。

- KMS Key の Key Policy を書き換える権限（`kms:PutKeyPolicy`）
- Lambda の関数のコードや設定を更新する権限
- Lambda の実行 Role を別の関数に渡す権限（`iam:PassRole`）
- Lambda の実行 Role の引き受けの条件を書き換える権限（`iam:UpdateAssumeRolePolicy`）

これらは Terraform で GATES を適用する権限と重なるため、取り除けません。
Lambda の関数の設定を更新できる主体は、発行上限、保護対象の一覧、リポジトリポリシーの適用も書き換えられます。
Terraform を適用できる主体を絞り、変更をレビューします。
GATES は、不正な署名を検知して通知する仕組みを持ちません。

### 1.8 秘密鍵のコピーと KMS Key を守る

担当：運用者

- インポートの後、手元に秘密鍵のコピーを残さない。インポートのコマンドはダウンロードしたファイルを削除するが、バックアップなどに写ったものは消せない
- Terraform の Plan に KMS Key の削除が現れたら、適用しない。削除した KMS Key の鍵素材は戻らない

## 2. GATES が守るもの

- **秘密鍵を渡さない**：GitHub App Private Key は KMS から取り出せない。ワークフロー、Runner、Lambda のどれも秘密鍵を持たない
- **呼び出し元を確かめる**：OIDC JWT の署名と内容を確かめ、呼び出し元を不変 Owner ID で許可オーナーと照合する
- **要求を超えて発行しない**：対象は要求したリポジトリだけ、権限は要求した権限だけ（GitHub が加える `metadata:read` を除く）で、すべてのリポジトリを対象にする手段はない
- **許可しない権限を含む要求は全体を拒否する**：Repository permissions でない権限か、発行上限が許さない権限を一つでも含む要求は、許可される権限だけに縮めずに拒否する。発行上限が高い水準を許していても、発行するのは要求した水準である
- **保護対象への要求を許可 Caller に限る**：保護対象を含む要求は、Caller の Repository ID と名前の両方が許可 Caller と一致し、要求した権限がどれもその権限の上限に含まれるときだけ通す。満たさない保護対象を一つでも含む要求は、保護対象でないリポジトリを含めて全体を拒否する
- **改名や作り直しで保護が外れない**：保護対象を改名して新しい名前で要求しても、削除して同じ名前で作り直したリポジトリを要求しても、トークンを返さない。許可 Caller のリポジトリを改名するか作り直すと、一覧を直すまで、そのリポジトリは許可 Caller に当たらない
- **リポジトリポリシーのないリポジトリに発行しない**：リポジトリポリシーを適用するデプロイでは、要求したどのリポジトリについても、そのリポジトリポリシーの許可 Caller と権限の上限で判定する。ファイルがない、ファイルでない、大きすぎる、一部でも誤りがあるリポジトリポリシーは、どの Caller も許さないものとして扱う。読めなかったときも、以前に読んだ内容を使わず、発行しない
- **リポジトリポリシーを読むトークンを外に出さない**：リポジトリポリシーを読むために取得するトークンは、`.github/gates-policy.yml` の読み取りだけの権限で、応答、ログ、監査記録のどこにも出さず、読み終えたら失効を試みる
- **発行されたトークンを照合する**：GitHub が返したトークンの対象と権限が要求と合わないか、対象の Repository ID と名前の組が保護対象の一覧と食い違えば、返さずに失効を試みる。リポジトリポリシーを適用するデプロイでは、リポジトリポリシーを読んだリポジトリと Repository ID が違う対象のトークンも返さない
- **確かめられなければ返さない**：検証、認可、署名、照合のどれかが成り立たなければ、トークンを返さない
- **資格情報を記録しない**：秘密鍵、OIDC JWT、トークン、AWS の一時認証情報を、監査記録にもログにも書かない

## 3. 残るリスク

### 3.1 リポジトリポリシーを適用しないデプロイ

- **一覧にないリポジトリは、自身への操作を GATES で制限できない**：GATES は、保護対象の一覧にないリポジトリへの要求では、Caller と対象の組み合わせを見ない。GitHub App の権限と発行上限が書き込みを含めば、許可オーナーのどのワークフローも、インストール対象のうち一覧にないどのリポジトリでも書き換えられる。新しく作ったリポジトリも、一覧に加えるまで同じである。リポジトリポリシーを適用するデプロイには、この箇条のリスクはない（許可した Caller の範囲で残るリスクは §3.2）
- **一覧にないリポジトリの Secrets とクラウドの権限に届き得る**：`contents:write` と `workflows:write` などを付与すると、許可オーナーのワークフローが、一覧にないリポジトリのワークフローを通して、そのリポジトリの Secrets や、そのリポジトリを信頼するクラウドの権限を使える
- **許可 Caller を経由して保護対象に届き得る**：許可 Caller のリポジトリがインストール対象に含まれ、保護対象でなければ、許可オーナーのどのワークフローも、そのリポジトリのワークフローを書き換えて、許可 Caller として保護対象を要求できる

### 3.2 リポジトリポリシーを適用するデプロイ

- **書き込める人と書き込みのトークンが許可を変えられる**：既定ブランチに書き込める人は、Admin でなくてもリポジトリポリシーを書き換えられる。`contents:write` か `administration:write` を許された Caller も、トークンで書き換えて自分にほかの権限を許せる。GATES は誰が変更したかを確かめない。越えさせたくない上限は保護対象の一覧で決める
- **許可した Caller の範囲では、適用しないデプロイと同じリスクが残る**：リポジトリポリシーが `contents:write` と `workflows:write` を許した Caller は、そのリポジトリのワークフローを通して、Secrets とクラウドの権限に届き得る。許可 Caller のリポジトリへの書き込みを許された Caller は、許可 Caller として、ほかのリポジトリにも届き得る
- **リポジトリポリシーは読まれ得る**：対象のリポジトリを読める人は、どのリポジトリが許可 Caller かを読め、許可 Caller を経由する経路の標的を選べる
- **複製でリポジトリポリシーが引き継がれる**：内容を複製して作ったリポジトリは、作った時点から複製元と同じ Caller と権限を許す
- **読んだ後の変更は、その要求に反映されない**：GATES がリポジトリポリシーを読んだ後に変更しても、その要求には古い内容で判定する
- **リポジトリポリシーを読むトークンは、GitHub 側に残り得る**：GATES の外には出さないが、失効に失敗したか、Lambda が途中で止まると、期限まで GitHub 側で有効に残る。読めるのは、主に `.github/gates-policy.yml` と、そこに置いたシンボリックリンクのリンク先である
- **リポジトリがインストール対象にあるかを見分けられる**：許可オーナーのワークフローは、インストール対象にないリポジトリの要求（`github_issuance_rejected`）と、インストール対象にあってリポジトリポリシーが拒否した要求（`authorization_denied`）を、エラーコードで見分けられる。リポジトリポリシーの内容は得られない
- **拒否される要求でも GitHub API の呼び出しが増える**：要求したリポジトリの数だけ GitHub からファイルを読むため、Installation のレート制限（1 時間に 5,000 回以上）を、1 回の要求で最大 12 回分、拒否される要求でも最大 11 回分消費する。許可オーナーのワークフローが拒否される要求を繰り返すと、ほかのワークフローの発行が止まり得る
- **適用に切り替えた時点で、リポジトリポリシーのないリポジトリへの発行が止まる**：拒否せずに記録だけする動作はない

### 3.3 どのデプロイにも残るリスク

- **許可 Caller のリポジトリの中は見分けない**：許可 Caller のリポジトリでワークフローを動かせる人は、ブランチ、イベント、ワークフローによらず、その許可 Caller に許した範囲を使える
- **保護対象の改名の直後は、GitHub 側でトークンが発行される**：保護対象を改名してから一覧を直すまで、新しい名前への要求のたびに GitHub はトークンを発行し、GATES は返さずに失効を試みる。失効に失敗したトークンは、Caller には渡らないまま期限まで有効に残る
- **Repository ID の再割り当てには備えていない**：GitHub が Repository ID をほかのリポジトリに割り当て直さないことは明記されていない。割り当て直されたリポジトリが許可 Caller と同じ名前を持つと、そのリポジトリは許可 Caller として扱われる
- **保護対象の一覧は秘密ではない**：Lambda の関数の設定、Terraform の State と Plan を読める人は、どのリポジトリが保護対象と許可 Caller かを読め、許可 Caller を経由する経路の標的を選べる
- **一覧やリポジトリポリシーを変えても、発行済みのトークンは失効しない**：保護対象を加えるか許可 Caller を外しても、それまでに発行したトークンは、期限まで発行したときの対象と権限で使える
- **トークンで行われた変更は、トークンの失効の後も残る**：書き換えたコードとワークフロー、追加されたデプロイキー、Webhook、コラボレーターは、トークンの期限が短くても、ジョブの終了時に失効しても取り消されない
- **失効は確実ではない**：Action はジョブの終了時に失効を試みるが、失敗しても、Runner が強制終了されても、トークンは期限（発行から 1 時間）まで使える。そのあいだは、要求したリポジトリに、要求した権限の操作ができる
- **漏れた資格情報の再利用は防げない**：漏れた OIDC JWT と AWS の一時認証情報は、それぞれの期限のあいだ、ジョブの外から GATES を呼び出すのに使える可能性がある。同じ OIDC JWT の再利用の検出と、要求の回数の制限は、将来の候補である
- **Grant は Key Policy を戻しても残る**：Key Policy を書き換えられた主体は、KMS Key に自分の署名を許す Grant を作れる。疑いがあれば、`aws kms list-grants --key-id <KMS Key の ARN>` で Grant を確かめ、覚えのない Grant を `aws kms revoke-grant --key-id <KMS Key の ARN> --grant-id <Grant ID>` で取り消す

## 4. 監査で追えること

GATES は、Lambda まで届いた要求ごとに監査記録を残します。
監査記録には、結果と失敗の理由、呼び出し元のリポジトリ、ワークフロー実行の ID、起動イベント、要求したリポジトリと権限が入ります。
ワークフロー実行の ID から、GitHub のワークフロー実行にたどれます。
保持期間の既定は 7 日のため、監査の方針に合わせて延ばします。

GATES の監査記録で追えないものもあります。

- **IAM が拒否した呼び出し**：Lambda に届かないため、AWS CloudTrail で調べる。IAM Role の引き受けは既定で記録されるが、Lambda の呼び出しは CloudTrail のデータイベントの記録を有効にしたときだけ残る
- **`pull_request_target` と `workflow_run` の起点**：これらの記録の ref とコミットは既定のブランチの値で、起点の Pull Request やワークフロー実行を一つに特定できるとは限らない。起点は、ワークフロー実行の ID から GitHub をたどって調べる
- **トークンで行われた操作**：監査記録に残るのは、要求したリポジトリと権限、発行の結果までである。トークンでどの操作が行われたかは、GitHub 側の記録で調べる
