# Security Design

## 1. Security Model

本システムでは、AWS IAM による Lambda Invoke の入口制御と、Lambda 内で検証した GitHub OIDC JWT に基づくトークン発行認可を分離します。GitHub App Private Key は AWS KMS に置き、Lambda は署名操作を KMS に依頼します。返却する Installation Access Token は、要求されたリポジトリと、要求された Repository permissions の権限に限定します。ただし、許可された付随権限は許容します。

コンポーネントの全体構成、JWT の生成元、正常系の処理順序は [System Architecture](architecture.md) に記述します。本ドキュメントは各境界が保証する内容と、認可・資格情報保護・拒否条件を定義します。概念の定義は [Domain Model](domain.md) を正本とします。

## 2. Trust Boundaries

| 境界 | 保証すること | 保証しないこと |
|---|---|---|
| AWS IAM / STS | 許可オーナーの不変 Owner ID を `sub` に含む GitHub OIDC JWT からだけ AWS 一時認証情報を発行し、特定 Lambda の Invoke のみ許可する | ワークフロー・リポジトリ単位のトークン発行認可、資格情報の現在の利用者の特定 |
| OIDC Verifier | GitHub JWT の真正性、Issuer、Audience、期限、不変 Owner ID と Repository ID を検証する | JWT と AWS 一時認証情報が同じジョブで取得されたことの証明、トークン発行権限そのもの |
| Authorization | 許可オーナーの Owner ID、取得した Installation の `account.id`、許可権限、発行上限、保護対象の一覧、明示された要求を照合する。リポジトリポリシーを適用するデプロイでは、各対象のリポジトリポリシーも照合する | リポジトリポリシーを適用しないデプロイでの、保護対象の一覧にないリポジトリのアクセス先ごとの Caller の制限、リポジトリポリシーの内容の正当性と変更した主体の確認、対象リポジトリが Installation に含まれることの事前確認、要求した権限が Installation に付与されていることの事前確認 |
| AWS KMS | 非抽出可能な秘密鍵による RSA 署名を実行する | 署名対象 JWT の内容に対する GATES の認可判断 |
| GitHub API | Installation と App の権限上限に従い短命トークンを発行する。リポジトリポリシーの取得では、対象のリポジトリの既定ブランチにある、指定したパスのファイルの内容を返す | GATES 側のトークン発行認可、`single_file:read` のトークンで指定したパスのほかを読めないこと（観測だけによる。§3.7）、取得した内容を誰が書いたか |

### 2.1 AWS IAM / STS

IAM Role の Trust Policy は、GitHub OIDC Provider を信頼先とし、Audience と、不変 Owner ID を含む `sub` の条件で引き受けを制限し、不変 ID を含まない旧形式の `sub` を拒否します。
AWS 用 OIDC JWT を検証するのは AWS STS だけで、Lambda はこの JWT を受け取りません。

- オーナー配下での共通利用を前提とし、`sub` の後半部分（`ref`、`pull_request`、`environment` など）による追加制限は設けない。許可オーナーのワークフローは共通の一つの IAM Role を引き受ける。
- 引き受けた IAM Role の権限は対象 Lambda への `lambda:InvokeFunction` のみとし、KMS `Sign`、IAM 管理、鍵インポートを許可しない。

オーナー側で既存リポジトリの OIDC JWT に不変 ID を含める設定が済んでいることを前提とします。この設定は GitHub 側の操作であり、GATES は実施しません。設定前のリポジトリは旧形式の `sub` を持つため、IAM Role を引き受けられません。

IAM は認証情報の由来となるオーナーに対する入口制限であるため、IAM 認証情報の窃取・再利用により、元のジョブ以外から Lambda Invoke が行われる可能性は残ります。

### 2.2 GATES 用 OIDC JWT

AWS 用 OIDC JWT とは別に、GATES 用 Audience の OIDC JWT を取得します。
Lambda はこの JWT を検証し、Caller を確定します。
署名と検証鍵、Issuer、Audience、時間条件、必須 Claim、`sub` と個別の ID の Claim の整合の受理条件は [OIDC JWT Claims](oidc-jwt-claims.md) と [OIDC JWT Signature](oidc-jwt-signature.md) に定めます。
検証鍵は固定した Issuer の JWKS からだけ得ます。
JWT の発行者と署名検証鍵を結び付け、JWT や要求の内容で鍵の取得先を変えられないようにするためです。

JWT が受理条件を満たしても、発行要求を認可したことにはなりません。
発行の可否は、認可条件で別に判定します。

AWS 一時認証情報と GATES 用 OIDC JWT が同じジョブで取得されたことを、暗号学的に検証しません。AWS IAM による Invoke の許可と、GATES 用 OIDC JWT に基づく発行認可は独立した境界です。トークンの発行可否は GATES 用 OIDC JWT と固定された許可条件から判断し、Docker Action 側の自己申告による照合を認可根拠としません。

### 2.3 Repository Policy

**リポジトリポリシー** は、アクセスされる側のリポジトリが、自分への要求を許す Caller と権限を定めたファイルで、そのリポジトリの既定ブランチに置きます（定義は [Domain Model](domain.md)）。
GATES は書式と意味を定めますが、内容は GitHub の上で、そのリポジトリの既定ブランチに書き込める主体が決めます。
そのため、リポジトリポリシーは、固定設定と異なり、レビューと Plan を経ない外部の入力です。
GATES は、誰がリポジトリポリシーを変更したかも、変更が正当であるかも確かめません。
GATES が保証するのは、読んだリポジトリポリシーが許す範囲を超えて発行しないことまでです（§3.7）。

## 3. Authorization

### 3.1 Authorization Rule

リポジトリへの発行は、次の条件がすべて成立した場合だけ許可します。
いずれかが成立しなければ、認可拒否として扱います。

1. 検証済み Caller の `repository_owner_id` が許可オーナーの不変 Owner ID と一致する。オーナー名の一致では代用しない。
2. 要求した各 `owner/repo` のオーナー名が固定された許可オーナー名と一致する。
3. 要求の Permissions の Permission Entry が、**どれも許可権限に含まれ、発行上限に水準の包含で含まれる**（§3.3）。
4. 要求した完全名のうち、リポジトリ名が保護対象の名前と一致するものすべてについて、Caller がその保護対象の許可 Caller に当たり、要求の Permission Entry がどれもその許可 Caller の権限の上限に水準の包含で含まれる（§3.6）。
5. リポジトリポリシーを適用するデプロイでは、要求した完全名のすべてについて、その対象のリポジトリポリシーの許可 Caller に Caller が当たり、要求の Permission Entry がどれもその許可 Caller の権限の上限に水準の包含で含まれる（§3.7）。

条件 1 から 3 は Caller と対象の組を見ず、条件 4 と 5 が組を見ます。
条件 4 か 5 を満たさない対象を一つでも含む要求は、ほかの対象を含めて全体を拒否します。
条件 1 から 4 は、固定設定と要求だけで判定できます。
条件 5 だけは、GitHub API から取得したリポジトリポリシーに依存するため、KMS と GitHub API を呼ぶ前の事前認可では判定できません。

Caller の `repository_id` は、監査と条件 4、5 に用います。
Caller のリポジトリ名（`sub` のリポジトリ部の名前）は、条件 4、5 で ID の一致に重ねて照合するためだけに用います。
ワークフロー起動属性は監査のための識別に用い、認可条件には含めません。
署名検証済みの Claims Set も監査記録に書き写すだけで、認証と認可のどちらにも使いません。

条件 3 の Permissions は、形式が正しければ JWT 検証後に認可条件として判定し、許可外なら認可拒否として扱います。
許可外の Permission Entry を一つでも含む要求は、許可されるものだけに縮小せず、全体を拒否します。
形式検証で先に落とさないのは、`members:read` のような許可外の要求を、認証済み Caller とともに監査記録に残すためです。
形式検証が入力不正にするのは、欠落や空の Permissions のように、要求した権限を読み取れない形に限ります。

要求には、全リポジトリを対象にする項目を設けません。
対象は要求で明示したリポジトリだけであり、`selected` しか許可しない値を利用者に指定させても、許可条件を一つ増やすだけになるためです。

条件 1 から 4 が成立した後、GitHub App JWT で許可オーナーの Installation を取得し、発行に使えるかを次の条件で確認します。

- Installation の `account.id` が許可オーナーの Owner ID と一致する。
- Installation が停止していない。停止状態を読み取れない応答は、停止していないと読まない。

どちらかが成立しなければ発行しません。
この拒否は利用者の要求に起因せず、運用者かオーナーの管理者が GitHub 側か固定設定を直す必要があるため、認可拒否と区別し、Installation 利用不可として返します。
停止中の Installation に対する発行 API の応答は公式文書で確認できていないため、GitHub の振る舞いに Fail Closed を預けず、取得した時点で閉じます。

リポジトリポリシーを適用しないデプロイでは、これらの確認の後に、Installation ID、要求した完全名、要求した Permissions を含む発行許可を生成します。
適用するデプロイでは、これらの確認の後にポリシー読み取りトークンを取得して各対象のリポジトリポリシーを読み、条件 5 が成立した後に発行許可を生成します（§3.7）。
どちらのデプロイでも、利用者に返す Installation Access Token は、発行許可を生成した後にだけ取得します。
Installation に対象リポジトリが含まれること、要求した Permissions が Installation に付与されていること、発行結果が発行許可に一致すること、実効対象のリポジトリ名と Repository ID の対応が保護対象の一覧と食い違わないこと、実効対象がリポジトリポリシーを読んだリポジトリと同じであることは、GitHub API の応答を受けてから確認します（§3.4）。一部だけで発行することや権限を暗黙に広げることは禁止します。

### 3.2 Installation Scope as Authorization Boundary

Installation の GitHub 側の仕様は [GitHub App Constraints](../external/github/app.md) を参照します。

リポジトリポリシーを適用しないデプロイでは、許可オーナーの有効なワークフローは、保護対象を除き、呼び出し元リポジトリ／チーム別の認可を経ず、GATES が許可する権限の範囲で GitHub App の Installation 対象リポジトリに横断的なトークン発行を要求できます。適用するデプロイでは、要求できるのは、各対象のリポジトリポリシーが許した範囲に限られます（§3.7）。どちらの場合も、この権限は GitHub App / Installation 自体の権限上限にも拘束されます。GATES が許可する権限は §3.3 に定めます。

GitHub App のインストール対象が、トークンで操作できる範囲の上限となります。`Only select repositories` により対象を限定できます。`All repositories` を使用すると、そのオーナーにインストールされた App の対象リポジトリ全体が操作できる範囲に含まれます。インストール対象の変更は認可境界の変更として扱います。
GATES はインストール対象を保持せず、発行のたびに GitHub が判定するため、変更は GATES の設定を変えずに以後の発行要求へ反映されます。対象から外したリポジトリを含む要求は GitHub が拒否し、GATES はどの対象にもトークンを返しません。

許可オーナーが Organization の場合、この変更は Organization オーナーだけの操作ではありません。
Organization オーナーが制限していなければ、リポジトリ管理者は自身の管理するリポジトリをインストール済みの App の対象に追加できます。
また、リポジトリに対する `installation_repositories:write` を持つ呼び出し元は、そのリポジトリを Installation に追加または削除できます。
追加されたリポジトリは、GATES と Installation が許可する権限の範囲で、許可オーナーの有効なワークフローから横断的にアクセスされ得ます。懸念は、非公開コードや設定、誤って格納された秘密情報の読み取りと、GitHub App に付与された権限による操作です。
このため、Organization の許可オーナーには、リポジトリ管理者によるインストールを Organization オーナーが制限していることと、`installation_repositories:write` の付与先を管理していることを、運用の前提として求めます。
GATES はこの設定を実行時に確認しません。

ここでの上限は、Installation Access Token の対象に指定できる範囲を指します。
「インストール対象の外にある公開リポジトリは読めない」を意味しません。
選択対象外の公開リポジトリは、発行の要求に含めると拒否されますが、発行したトークンでは公開の内容として読めます（[GitHub App Constraints](../external/github/app.md)）。
公開の内容は誰でも読めるため、この振る舞いは読み取れる範囲を広げません。
`contents:write` のトークンは選択対象外のリポジトリに書き込めませんでしたが（同）、ほかの読み取り以外の権限で選択対象外の公開リポジトリに何ができるかは確かめていません。

GATES は、デプロイ時に固定した GitHub App と許可オーナーの組から Installation が一意に決まるものとして扱います。
これは、オーナーを指定して単一の Installation を返すエンドポイントがあることからの推論であり、GitHub が一意性を明示的に保証したものとは扱いません。
Lambda は Installation ID を設定として持たず、固定したオーナーの Installation を GitHub API から取得し、`account.id` の一致で確認します（[Requirements](../spec/requirements.md) FR-OPS-001）。
そのため実行時の入力から Installation を指定する余地はなく、オーナーの名前変更やアプリの再インストールが起きても、固定した不変 Owner ID と異なる Installation へ発行しません。

### 3.3 Permission Boundary

GATES が発行を許可する Permission Entry の集合を、許可権限と呼びます。
許可権限は、GitHub が Repository permissions に分類する権限名と、GitHub が要求どおりに発行する水準の組です。
権限名、水準、分類の根拠は [GitHub App Constraints](../external/github/app.md) の「権限名と分類」を参照します。

許可権限は、次の規則で定めます。

- **列挙して固定する**：発行 API のスキーマは、権限名を Repository、Organization、Account、Enterprise に分けて示さない。そのため GATES は、許可する権限名と水準を列挙して持ち、列挙にない権限名と水準を認可拒否にする。GitHub が権限を加えても、GATES が列挙に加えるまで発行しない。権限名の形から分類を推定すると、GitHub が加えた Organization permissions を発行し得るためである
- **分類と水準を確かめたものだけを加える**：列挙に加えるのは、ユーザーアカウントの Installation の `permissions` に現れた権限名と、その権限名で要求どおりに発行されることを確かめた水準に限る。Organization permissions と Enterprise permissions は Organization か Enterprise にインストールした場合にだけ効き、Account permissions はインストールではなくユーザーの認可で付与されるため、ユーザーアカウントの Installation に現れた権限名を Repository permissions に当たるものとして扱う（[GitHub App Constraints](../external/github/app.md)）
- **発行 API のスキーマに権限名があることを条件にしない**：スキーマに権限名がない Repository permissions も、上の条件を確かめたものは列挙に含め、水準もスキーマではなく GitHub の応答で決める。GitHub App に付与された権限を利用者が明示して要求したとき、スキーマの有無で拒否すると、GitHub が発行する権限を GATES の判断で狭めることになるためである。スキーマにない権限名は、GitHub が名前や扱いを予告なく変える可能性があるが、変わった場合も、発行 API の拒否か照合（§3.4）の失敗でトークンを返さずに終わる
- **Organization permissions、Account permissions、Enterprise permissions は発行しない**：これらは対象リポジトリを明示しても影響範囲が狭まらず、リポジトリを単位とする認可条件と照合（§3.4）では範囲を限定できない
- **Caller と対象によって変えない**：許可権限は、どの Caller にも、どの対象リポジトリにも同じである。一つの要求の Permissions は、その要求のすべての対象に同じく適用される。保護対象の一覧（§3.6）は、許可権限の中で、保護対象ごとに Caller と権限を狭めるだけである
- **設定で広げない**：許可権限を広げる設定を持たない。デプロイごとに狭める手段は、次に定める発行上限である

GATES 運用者は、許可権限のうち、そのデプロイで発行してよい Permission Entry の集合を、デプロイ時の設定として決めます。
この集合を **発行上限** と呼びます。
GitHub App に付与する権限は GitHub の画面だけで変えられ、コードのレビューにも Terraform の Plan にも現れません。
発行上限を Terraform の入力にすると、発行できる権限の変更がレビューと Plan の対象になり、GitHub App に誤って権限を付与しても、発行上限に含まれない権限は発行しません。

発行上限は、次の規則で定めます。

- **許可権限の一部に限る**：許可権限に含まれない Permission Entry を発行上限に含めると、Lambda の初期化が失敗し、どの要求も受け付けない。許可権限は Organization permissions などを発行しないための最後の上限であり、設定から広げる手段を持たない
- **水準の包含で照合する**：発行上限は許可権限と同じく Permission Entry の集合で、一つの権限名に複数の水準を含められる。要求の Permission Entry は、許可権限に含まれ、発行上限が同じ権限名の同じかより高い水準を含むときに許す（水準は `read`、`write`、`admin` の順に高い）。`contents:write` だけを含めた発行上限は、`contents:read` の要求を許す。GitHub App に付与した水準より低い水準の要求は要求どおりに発行されたため（[GitHub App Constraints](../external/github/app.md) §4.4 の観測）、高い水準を発行してよいデプロイで低い水準を拒否しても、守れる範囲は増えない
- **要求した水準で発行する**：発行上限は要求を許すかだけを決め、発行する水準を変えない。上限が `contents:write` でも、`contents:read` の要求には `contents:read` を発行し、発行結果の照合（§3.4）も要求した水準との一致を求める
- **空にしない**：空の発行上限はどの要求も認可しない設定で、書き損じと区別できないため、初期化の失敗にする
- **付随権限には適用しない**：付随権限 `metadata:read` は要求にかかわらず GitHub が付与するもので、発行結果の照合で許容する。発行上限に含まれなくても、保護対象を含む要求で許可 Caller の権限の上限（§3.6）に含まれなくても、リポジトリポリシーで Caller が当たる許可 Caller の権限の上限（§3.7）に含まれなくても許容する。`metadata` を明示して要求するときは、ほかの権限と同じく発行上限に含まれている必要がある
- **Caller と対象によって変えない**：発行上限はデプロイに一つで、どの Caller にも、どの対象リポジトリにも同じに効く。Caller と対象の組による制限は、保護対象の一覧（§3.6）とリポジトリポリシー（§3.7）が担う
- **ポリシー読み取りトークンには適用しない**：ポリシー読み取りトークンの `single_file:read` は GATES が固定する権限で、利用者の要求ではないため、発行上限に含まれることを求めない。Caller が `single_file:read` を要求するときは、ほかの権限と同じく発行上限に従う
- **以後の発行要求にだけ効く**：発行上限を狭めても、発行済みのトークンは失効させない。発行済みのトークンは、GitHub が定めた有効期限まで、発行したときの権限で使える。Lambda の設定の更新が完了するまでの呼び出しは、更新前の発行上限で判定される（§5）

発行上限は Lambda の環境変数として渡すため、Lambda の設定を変更できる主体は、発行上限を許可権限まで広げられます。
この主体は関数のコードも変更して実行 Role の権限で署名させられるため、発行上限を広げられても、得られる能力は増えません。
発行上限が抑えるのは、GitHub App に誤って付与した権限と、レビューと Plan を経ずに GitHub の画面で広げた権限の発行です。
Lambda の設定やコードを変更できる主体による悪用は抑えません。

発行できる権限は、許可権限と発行上限に加えて、GitHub App と Installation に付与された権限にも拘束されます。
GATES は Installation に付与された権限を事前に確かめません。
付与されていない権限か水準を含む要求は、発行 API が拒否するか、その権限を除いて発行するかのどちらかで（[GitHub App Constraints](../external/github/app.md)）、後者は照合が実効権限の欠落として検出します（[Requirements](../spec/requirements.md) FR-AUTHZ-007）。
どちらになるかは GitHub の振る舞いに依存するため、トークンを返さないことは照合で保証します。
GitHub App / Installation の付与権限が要求より広くても、発行するトークンの権限は要求した Permissions から拡大しません。付随する `metadata:read` のみ、照合時に許容します。

### 3.4 Issuance Result Verification

- GitHub API に発行を要求するときは、発行許可の対象と Permissions を必ず指定する。
- 発行応答の対象リポジトリと実効権限を発行許可に照合する。Owner ID、Repository ID の有効性・一意性、対象の全件一致を確認し、必要な情報の欠落、対象外のリポジトリ、過大な権限があればトークンを返却しない。この拒否は GitHub API の通信障害とは別のエラーとして返し、監査記録に Caller とともに残す。
- GitHub の発行応答からトークン文字列を取得でき、照合に失敗した場合は、利用者へ返却せず失効 API の呼び出しを試みる。失効はベストエフォートとし、試行の成否を監査記録に残す。API 応答が失われた場合はトークンの発行有無が不明となり得る。
- 実効権限は、権限名と水準の組で発行許可の Permissions に照合する。発行許可の Permission Entry が実効権限に一つでも欠けているか、水準が異なれば、トークンを返却しない。水準が要求より低い場合も、要求を縮小した発行として拒否する。
- 要求にかかわらず GitHub が付与する `metadata:read` だけは、発行許可の Permissions になくても、応答に含まれていれば許容する。付与の条件は未確認であり（[GitHub App Constraints](../external/github/app.md)）、含まれなくても拒否しない。`metadata` を要求した場合は、ほかの権限と同じく発行許可の水準に照合する。GitHub がほかの権限を加えるように変えた場合、その応答は照合の失敗になる。
- 発行応答の `repository_selection` が `selected` であることを確認する。`all` は Installation の全リポジトリを対象にしたことを意味し、要求外の対象を含むため返却しない。
- 各実効対象と各保護対象の組について、実効対象のリポジトリ名が保護対象の名前と一致することと、実効対象の Repository ID が保護対象の ID と一致することが、両方成り立つか両方成り立たないことを確認する。一方だけが成り立つ実効対象は、保護対象の一覧と GitHub の現在の状態が食い違っており（§3.6）、照合の失敗としてトークンを返却しない。
- リポジトリポリシーを適用するデプロイでは、各実効対象の Repository ID が、同じ完全名でリポジトリポリシーを読んだ対象（照合済みのポリシー読み取りトークンの実効対象）の Repository ID と一致することを確認する。一致しない実効対象を含む発行結果は、リポジトリポリシーを読んだ後に対象が削除され、同じ名前で作り直された場合などに当たり、照合の失敗としてトークンを返却しない。
- 応答の Repository ID は、ID の有効性と一意性の確認、保護対象の一覧との照合、リポジトリポリシーを読んだ対象との照合、監査に使う。GATES は要求の時点で対象の Repository ID を確かめないため、応答の Repository ID が利用者の意図したリポジトリの ID であることは示さない。

ポリシー読み取りトークンの発行応答も、権限を除き、利用者に返すトークンと同じ条件（対象の全件一致、Owner ID、Repository ID の有効性と一意性、`repository_selection`、保護対象の名前と ID の対応）で照合します。
実効権限は `single_file:read` と付随権限だけで、`single_file:read` を欠いてはならず、読めるファイルのパスは GATES が固定したパスだけでなければなりません。
照合に失敗したポリシー読み取りトークンは、リポジトリポリシーの取得に使わず、失効を試みます。
発行応答のパスの値は、`README.md` をパスに指定した観測でだけ確かめており（[GitHub App Constraints](../external/github/app.md) §4.4、§4.5）、パスの値を読み取れない応答は照合の失敗になります。

対象の全件一致を照合するため、[Requirements](../spec/requirements.md) FR-AUTHZ-005 のうち範囲外の対象を含む要求にトークンを返さないことは、GitHub が範囲外の対象を拒否するかどうかに依存しません。
GitHub が範囲外の対象を黙って除いて発行した場合は、応答の対象と発行許可の不一致を検出し、トークンを返さず、取得したトークンの失効を試みます。
発行 API が呼び出しを `422` で拒否した場合は GitHub 発行拒否、発行応答を取得して照合が失敗した場合は照合失敗とします。どちらも、発行前の GATES の認可条件による認可拒否とは区別します。
GitHub 側での失効成功や、応答喪失で取得できなかったトークンの不存在は保証せず、GitHub 側で有効なまま残る可能性があります。

### 3.5 Accepted Risks without Repository Policies

リポジトリポリシーを適用しないデプロイでは、保護対象の一覧にないリポジトリについて、認可条件が Caller と対象の組み合わせを見ません。
そのため、許可オーナーのどのワークフローも、Installation に含まれるそれらのリポジトリに対して、GitHub App に付与され、発行上限に含まれる Repository permissions をすべて要求できます。
保護対象の一覧にないリポジトリは、自身に対する操作を GATES の認可では制限できません。
新しく作ったリポジトリも、一覧に加えるまでは同じです。
[Scope](../spec/scope.md) がこの組み合わせを、リポジトリポリシーを適用しないデプロイのスコープとするため、次のリスクを受容します。
各権限で呼べる API は、GitHub の公式資料（[Permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps)）に基づきます。

- **ほかのリポジトリの変更と破壊**：`contents:write` はコミット、ブランチ、タグ、リリースを書き換えられる。`administration:write` はリポジトリの設定の変更と削除、ブランチ保護と ruleset の変更、コラボレーターとデプロイキーの追加、セルフホストの Runner の登録に届く。リポジトリの削除や履歴の書き換えのように、元に戻せない操作を含む
- **ほかのリポジトリの Secrets と OIDC への到達**：`contents:write` と `workflows:write` を持つトークンは、ほかのリポジトリのワークフローのファイルを書き換えられる。書き換えたワークフローは、そのリポジトリのワークフローとして動き、ブランチと Environment の保護が止めない範囲で、そのリポジトリの Secrets と、そのリポジトリを主体とする OIDC JWT を使える。`secrets:write` は Secrets の値を読めないが、上書きと削除ができる。`actions:write` は、ワークフローの起動、実行ログの削除、OIDC JWT の `sub` のカスタマイズの変更に届く。このため、Installation に含まれるリポジトリの Secrets と、それらのリポジトリを信頼する外部の権限（クラウドの Role など）は、許可オーナーのどのワークフローからも到達され得るものとして扱う
- **要求した対象を越える変更**：公式資料は、`installation_repositories:write` で使える API に、リポジトリを Installation に加える API と外す API を挙げる。Installation の対象は GATES の認可の境界であり、許可オーナーのワークフローが、その境界を変え得るトークンを要求できる。`repository_creation:write` で使える API には、リポジトリの作成、フォーク、テンプレートからの生成を挙げる（ほかの権限も要る場合がある）。どちらも、要求した対象のリポジトリに影響範囲を限れない。トークンで実際に何ができるかは確かめていない
- **トークンの有効期限より長く残る変更**：デプロイキー、Webhook、コラボレーター、書き換えたワークフローとコードは、トークンの失効と有効期限の後も残る。トークンが短命であることと、ジョブの終了時の失効は、トークンで行われた変更を取り消さない
- **信頼できないコードが得る権限の拡大**：トークンを取得するジョブで信頼できないコードが動くと、そのコードは読み取りにとどまらず、GitHub App に付与された権限で Installation のリポジトリを操作できる
- **機密の情報の読み取りの拡大**：`secret_scanning_alerts:read` は検出された秘密情報のアラートに、`actions:read` はほかのリポジトリの実行ログと成果物に届く。読み取れる範囲はリポジトリの内容にとどまらない
- **トークンで行われた操作の追跡**：GATES の監査記録が残すのは、Caller、要求対象、要求権限、発行の結果までである。発行したトークンでどの操作が行われたかは GATES に残らず、GitHub 側の記録に依存する

これらのリスクは、次の手段で抑えます。
リポジトリポリシーの適用、発行上限、保護対象の一覧は、GATES が発行のたびに確かめる GATES の設定です。
残りは GATES の外の設定であり、GATES は実行時に確かめません。

- **リポジトリポリシーを適用する**：適用するデプロイでは、どの対象への要求も、その対象のリポジトリポリシーが許した Caller からの、許した権限の範囲の要求に限られる。新しく作ったリポジトリも、リポジトリポリシーを置くまでどの Caller からも要求できない。ただし、リポジトリポリシーを持つリポジトリの内容を複製して作ったリポジトリは、作った時点で複製元と同じリポジトリポリシーを持ち得る（§3.7 の複製による引き継ぎ）。上のリスクのうち、許可オーナーのどのワークフローからも到達されるという前提はなくなり、到達できるのは、到達先のリポジトリポリシーが許した Caller のリポジトリでワークフローを動かせる者に限られる。許した Caller の範囲で同じリスクは残り、リポジトリポリシーそのものに伴うリスクが加わる（§3.7）
- **守りたいリポジトリを保護対象にする**：操作できるワークフローを一部のリポジトリのものに限りたいリポジトリは、保護対象の一覧に加え、要求できる Caller と権限を限る。上の経路で到達されたくないリポジトリ（Secrets を持つリポジトリや、外部の権限に信頼されたリポジトリなど）も対象になる。一覧の変更は、発行上限と同じく Terraform の変更としてレビューと Plan を経る。保護対象に残るリスクは §3.6 に定める
- **発行上限を限る**：GitHub App に付与し、かつ発行上限に含まれる Repository permissions が、許可オーナーのすべてのワークフローに共通の上限になる。発行上限は、許可オーナーのワークフローが必要とする権限だけにする。発行上限の変更は、Terraform の変更としてレビューと Plan を経る
- **GitHub App に付与する権限を限る**：`administration`、`workflows`、`secrets`、`actions`、`installation_repositories`、`repository_creation` の `write` は、上の経路のうち影響の大きいものを開くため、必要な自動化がある場合に限って付与する。発行上限が狭くても、GitHub App に付与した権限は署名能力の悪用で得られるため、GitHub App にも必要な権限だけを付与する。GitHub App の権限の変更は、Installation の対象の変更と同じく、認可境界の変更として扱う
- **Installation の対象を限る**：保護対象にしないリポジトリは、GitHub App に付与した権限で、許可オーナーのどのワークフローから操作されてもよいものに限る。保護対象にするかどうかにかかわらず、GATES の Docker Action と Terraform のコードを置くリポジトリや、GATES の AWS リソースを変更できる Role に信頼されたリポジトリを対象に含めると、GATES 自身の改ざんに届く経路ができるため、含めない
- **アクセスされる側のリポジトリで保護する**：ブランチ保護と ruleset は、GitHub App を bypass の対象に加えない限り、トークンによる変更にも適用される見込みである（公式資料が bypass の対象に App を挙げることからの推論で、実環境では確かめていない）。`administration:write` を持つトークンはこの保護を変更できるため、保護に頼る場合は GitHub App に `administration:write` を付与しない

### 3.6 Protected Repositories

GATES 運用者は、操作できるワークフローを一部のリポジトリのものに限りたいリポジトリを **保護対象** として固定設定の保護対象の一覧に指定し、要求できる Caller と権限を限ります（[Requirements](../spec/requirements.md) FR-AUTHZ-009）。
保護対象、許可 Caller、権限の上限の定義は [Domain Model](domain.md) を正本とします。

保護対象の一覧は、次の規則で定めます。

- **Repository ID で同定し、名前で発行前に見分ける**：発行要求は対象を完全名だけで示すため、要求のリポジトリ名が保護対象の名前と一致する対象を保護対象として、発行前に §3.1 の条件 4 を判定する。発行の後は、実効対象の Repository ID を保護対象の ID と照合する（§3.4）。Repository ID を同定に使うのは、改名で変わらないと GitHub が定め（[GitHub Actions OIDC Constraints](../external/github/oidc.md) の GH-OIDC-REPOSITORY-ID-RENAME）、削除して作り直したリポジトリでは別の値だったため（[GitHub Owner and Repository Constraints](../external/github/account.md) §3 の観測）である。ほかのリポジトリに再び割り当てられないことは、GitHub が ID を「immutable」と呼ぶことからの推論で、明記はない（同 §3）
- **一覧と GitHub の食い違いを拒否に倒す**：名前で見分ける発行前の判定と、ID で突き合わせる発行後の照合は、片方だけでは保護にならない。組にすると、一覧と GitHub の現在の状態が食い違ったどの場合も、トークンを返さずに終わる（次の表）
- **許可 Caller は ID と名前の両方で照合する**：許可 Caller に当たるのは、Caller の `repository_id` と、`sub` のリポジトリ部の名前の両方が一致する Caller に限る。名前は `sub` から得る。`sub` は署名と形式の検証を経ており、しかも同じ文字列の中で名前と Repository ID が組になっているためである。名前の照合は ID の一致に重ねる条件であり、名前だけが一致する Caller を許可 Caller にしない。ID と名前のどちらを書き誤っても、その許可 Caller はどの Caller にも当たらず、拒否に倒れる
- **許可 Caller の権限の上限は許可権限の一部に限り、発行上限の一部であることは求めない**：許可権限に含まれない組を権限の上限に含めると、Lambda の初期化が失敗する。発行上限に含まれることを求めると、発行上限を狭めただけで初期化が失敗し、どの要求も受け付けなくなる。発行上限の外の組は §3.1 の条件 3 が拒否するため、許す範囲は広がらない
- **条件を加えるだけにする**：保護対象の一覧は、§3.1 の条件 1 から 3 と 5、Installation の条件、GitHub App に付与された権限の条件で拒否される要求を許可に変えず、保護対象を含まない要求の結果も変えない
- **リポジトリポリシーと重ねる**：リポジトリポリシーを適用するデプロイでは、保護対象もリポジトリポリシーに従う。保護対象への要求は、保護対象の一覧とリポジトリポリシーの両方が許すときだけ許可し、どちらかが優先して他方を上書きすることはない。そのため、保護対象の一覧は、保護対象のリポジトリポリシーを書き換えられる主体（§3.7 の書き込みのトークンを含む）が越えられない上限になる
- **欠落させない**：保護対象の一覧の欠落と不正な値は、Lambda の初期化の失敗にし、どの要求も受け付けない。保護対象を置かないデプロイは、空の一覧を明示する。欠落を「保護なし」と読むと、設定の漏れで保護が外れるためである
- **以後の発行要求にだけ効く**：一覧を変えても、発行済みのトークンは失効させない。Lambda の設定の更新が完了するまでの呼び出しは、更新前の一覧で判定される（§5）

一覧と GitHub の状態が食い違ったときの結果は次のとおりです。

| 出来事 | 発行前 | 発行後 | 結果 |
|---|---|---|---|
| 保護対象を改名し、新しい名前で要求 | 名前が一覧にないため通る | Repository ID が保護対象の ID で、名前が一致しない | 照合失敗 |
| 保護対象を改名し、旧名で要求 | 名前で保護対象と判定する | GitHub が `422` で拒否し、発行結果がない（[GitHub App Constraints](../external/github/app.md) §4.2 の観測。GitHub は保証していない） | 認可拒否か GitHub 発行拒否 |
| 保護対象を削除し、同じ名前で作り直して要求 | 名前で保護対象と判定する | 名前が一致し、Repository ID が一致しない | 認可拒否か照合失敗 |
| 一覧の保護対象の ID を書き誤る | 名前で保護対象と判定する | 名前が一致し、Repository ID が一致しない | 認可拒否か照合失敗 |
| 一覧の保護対象の名前を書き誤る | 名前が一覧にないため通る | Repository ID が保護対象の ID で、名前が一致しない | 照合失敗 |
| 許可 Caller のリポジトリを改名する | Repository ID は一致し、名前が一致しない | なし | 認可拒否 |
| 許可 Caller のリポジトリを削除し、同じ名前で作り直す | 名前は一致し、Repository ID が一致しない | なし | 認可拒否 |

照合失敗になる行では、GitHub 側でトークンが一度発行され、GATES は利用者に返さずに失効を試みます。
一覧を直すまで、その保護対象への発行は止まります。
保護対象の条件による認可拒否は、ほかの認可拒否と同じく、監査記録の拒否の理由に満たさなかった条件として残り、一覧の ID と名前は記録しません（[Domain Model](domain.md) の Audit Record）。

Caller の名前と ID の出どころには、GitHub が保証していない前提があります。
`sub` のリポジトリ部の名前は、観測では REST API の `name` と大文字小文字まで一致し、改名の後に発行された JWT では新しい名前でしたが、GitHub はこれを定めていません（[GitHub Actions OIDC Constraints](../external/github/oidc.md) の GH-OIDC-REPOSITORY-NAME-OBSERVED、GH-OIDC-REPOSITORY-NAME）。
運用者が REST API で調べて一覧に書く Repository ID が JWT の `repository_id` と同じ値であることも、観測だけに依ります（同 GH-OIDC-REPOSITORY-ID-REST-OBSERVED、GH-OIDC-REPOSITORY-ID-REST）。
どちらの前提が崩れても、許可 Caller に当たる Caller が減るだけで、拒否に倒れます。

保護対象の一覧は Lambda の環境変数として渡すため、Lambda の設定を変更できる主体は、一覧を書き換えて保護を外せます。
発行上限と同じく（§3.3）、この主体は関数のコードも変更できるため、得られる能力は増えません。
一覧が抑えるのは、保護対象への要求のうち、レビューと Plan を経た一覧に載っていない Caller や権限によるものです。

保護対象について、次のリスクを受容します。

- **許可 Caller を経由した到達**：許可 Caller のリポジトリが Installation の対象に含まれ、保護対象でない場合、許可オーナーのどのワークフローも、`contents:write` と `workflows:write` のトークンでそのリポジトリのワークフローを書き換え（§3.5）、許可 Caller として保護対象を要求できる。発行上限と GitHub App の権限が書き込みを含むデプロイでは、許可 Caller のリポジトリも保護対象にするか、Installation の対象から外す。リポジトリポリシーを適用するデプロイでは、許可 Caller のリポジトリへの書き込みにも、そのリポジトリのリポジトリポリシーの許可が要るため、この経路を使えるのは、そのリポジトリポリシーが書き込みを許した Caller のワークフローを動かせる者に限られる
- **Caller の粒度**：Caller はリポジトリ単位で、ブランチ、イベント、ワークフローを見分けない。許可 Caller のリポジトリでワークフローを動かせる者は、その許可 Caller に許した範囲を使える。`pull_request_target` のように信頼できないコードがトークンを得る経路（§5）も、許可 Caller のリポジトリでは保護対象に届く
- **一覧の公開範囲**：保護対象の一覧は非秘密値として、Terraform の State と Plan、Lambda の関数の設定に残る。関数の設定を読める主体は、どのリポジトリが保護対象で、どのリポジトリが許可 Caller かを読め、許可 Caller を経由した到達の標的を選べる
- **許可 Caller の改名と作り直し**：許可 Caller のリポジトリを改名するか作り直すと、一覧を直すまで、そのリポジトリのワークフローは保護対象を要求できない
- **改名の直後の発行**：保護対象を改名してから一覧を直すまで、新しい名前への要求のたびに GitHub 側でトークンが発行され、照合失敗で失効を試みる。失効は成功を保証しない（§3.4）
- **Repository ID の再割り当て**：GitHub が Repository ID をほかのリポジトリに再び割り当て、そのリポジトリが許可 Caller と同じ名前を持つと、そのリポジトリは許可 Caller として扱われる。GitHub は再び割り当てないことを明記していない。名前も同じでなければ拒否に倒れるため、このリスクを受容する
- **YAML を読む外部のライブラリ**：Lambda は保護対象の一覧を読むため、外部の YAML のライブラリ一つに依存する。ライブラリの欠陥は、一覧の読み違いか初期化の失敗として現れ得る。読ませるのは運用者が書いた環境変数と、リポジトリポリシーを適用するデプロイで取得したリポジトリポリシーだけで、利用者の Payload は読ませない。リポジトリポリシーは運用者ではなく対象のリポジトリに書き込める主体が書くため、ライブラリの欠陥は、その主体が細工した文書による読み違いや資源の消費としても現れ得る。認可に要らない YAML の機能（アンカー、エイリアス、タグ、重複したキーなど）を拒否し、読む前に大きさを限り、読んだ値を不変条件（[Domain Model](domain.md) の INV-016、INV-017）で確かめてから使うため、ライブラリの解釈が書いた主体の意図と分かれる範囲を狭める。ライブラリは脆弱性の検査と依存の更新の対象に含め、使う箇所を一つに限る

### 3.7 Repository Policies

アクセスされる側のリポジトリは、自分への要求を許す Caller と権限を、リポジトリポリシーで決めます（[Requirements](../spec/requirements.md) FR-AUTHZ-011）。
リポジトリポリシー、ポリシー読み取りトークン、リポジトリポリシーの適用の定義は [Domain Model](domain.md) を正本とします。
GATES 運用者は、リポジトリポリシーを適用するかしないかを、デプロイごとに固定設定で決めます。

リポジトリポリシーは、次の規則で定めます。

- **変更できる主体を GitHub の書き込み権限に委ねる**：リポジトリポリシーを変更できるのは、GitHub がそのリポジトリの既定ブランチへの書き込みを許した主体である。GATES は、リポジトリの管理者の名簿、独自の承認、変更した主体の確認を持たない。誰がリポジトリに書き込めるかは GitHub の権限の設定で決まり、GitHub 側の設定と操作は GATES の対象外である（[Constitution](../CONSTITUTION.md) の Non-Goals）。GATES の側に別の名簿や承認を持つと、書き込める主体を二か所で決めることになるためである。ブランチ保護、ruleset、CODEOWNERS で変更できる主体を絞るかはリポジトリの管理者が決め、GATES はそれらがあることを前提にしない
- **すべての対象に課す**：適用するデプロイでは、保護対象かどうかを問わず、要求したすべての対象に §3.1 の条件 5 を課す。Caller が自分のリポジトリを対象にする場合も例外にしない。条件 5 を課す対象を保護対象の一覧で選ぶ形にしないのは、すべての対象に同じ条件を課せば、既定の拒否に例外がなく、判定の分岐も増えないためである
- **許可 Caller は保護対象の一覧と同じ条件で照合する**：Caller が許可 Caller に当たるのは、Repository ID とリポジトリ名の両方が一致する場合に限る（§3.6）。リポジトリポリシーの変更をレビューする人は名前で許可を判断するため、ID だけを照合すると、名前の示すリポジトリとは別のリポジトリを許可する書き誤りや偽装に気付けない。代わりに、Caller のリポジトリを改名すると、各対象のリポジトリポリシーを直すまで拒否される
- **既定で拒否する**：有効なリポジトリポリシーがない対象（ファイルがない、パスにあるのがファイルでない、大きすぎる、書式か内容が不正）を含む要求は、どの Caller からでも拒否する。文書の一部だけが不正な場合も、文書全体を無効とし、正しい部分だけを使わない。ないことを許可と読むと、ファイルを消すだけで制限が外れるためである。どの Caller にも許可しない文書は、許可 Caller の空の集合を明示する
- **権限の上限は許可権限の一部に限り、発行上限の一部であることは求めない**：許可権限に含まれない組を一つでも含む文書は不正とする。発行上限に含まれることを求めない理由は、保護対象の一覧と同じである（§3.6）
- **取得できなければ発行しない**：GitHub API の障害でリポジトリポリシーを読めない対象を含む要求には、発行しない。以前に読んだ内容を使わず、許可とも読まない
- **既定ブランチの現在の内容を読む**：パスは GATES が固定し、Caller はパス、ref、取得先を指定できない。発行処理のたびに読み、保持しない
- **条件を加えるだけにする**：リポジトリポリシーは、§3.1 の条件 1 から 4、Installation の条件、GitHub App に付与された権限の条件で拒否される要求を許可に変えない。発行する水準は、要求した水準のままである
- **適用を明示させる**：リポジトリポリシーの適用に既定値を置かず、欠落と不正な値は Lambda の初期化の失敗にする。欠落を「適用しない」と読むと、設定の漏れで既定の拒否が外れ、「適用する」と読むと、更新しただけでリポジトリポリシーのない対象への発行が止まるためである
- **以後の発行要求にだけ効く**：リポジトリポリシーを変えても、発行済みのトークンは失効させない。発行処理がリポジトリポリシーを読んだ後の変更は、その発行処理に反映されない

リポジトリポリシーを適用するデプロイの発行処理は、§3.1 の Installation の確認の後、次の順に進みます。

1. ポリシー読み取りトークンを発行する。対象は要求した完全名、権限は `single_file:read` だけである
2. 発行応答を照合する（§3.4）。照合に失敗したら、失効を試み、照合失敗で終わる
3. 照合済みのポリシー読み取りトークンで、各対象のリポジトリポリシーを読む
4. 取得の成否にかかわらず、ポリシー読み取りトークンの失効を試みる
5. 読めなかった対象があれば、一時的な障害で終わる。すべての対象を読めたら §3.1 の条件 5 を判定し、成立すれば発行許可を生成する
6. 利用者に返すトークンを要求した完全名で発行し、照合する。照合は、各実効対象の Repository ID が、手順 2 の実効対象の Repository ID と一致することを含む

対象の Repository ID は、ポリシー読み取りトークンの発行応答から得ます。
発行応答は、名前で指定した対象ごとに Repository ID、Owner ID、完全名を返すため（[GitHub App Constraints](../external/github/app.md) §4.2 の公式資料の応答例と観測）、ID を調べるための呼び出しを加えません。

リポジトリポリシーの取得は名前でファイルを読み、その応答は、読んだリポジトリを Repository ID で示しません。
そのため、ポリシー読み取りトークンの発行と取得の間に、名前が別のリポジトリを指すように変わる競合は残ります。
この競合を起こすには対象のリポジトリの改名か削除が要り、その権限を持つ主体は、対象のリポジトリポリシーも書き換えられます。
競合で得られる許可は、その主体がリポジトリポリシーの書き換えでもともと与えられる許可を超えないため、取得の前後に対象の情報を取り直す照合は加えません。

ポリシー読み取りトークンは、リポジトリポリシーによる認可の前に取得する資格情報です。
認可が成立する前に取得するトークンの、取得する機会と使える範囲を狭めるため、次の規則で扱います。

- **取得してよい要求を限る**：§3.1 の条件 1 から 4 と Installation の条件がすべて成立した要求に対してだけ取得する（[Requirements](../spec/requirements.md) FR-ISSUANCE-002、FR-ISSUANCE-007）
- **権限と対象を固定する**：権限は `single_file:read` だけ、対象は要求した完全名だけとし、利用者の入力から権限、対象の追加、読むパスを指定させない
- **GATES の外に出さない**：リポジトリポリシーの取得にだけ使い、利用者に返さず、応答、ログ、監査記録に書かない
- **使い終えたら失効を試みる**：取得の成否と、その後の発行処理の結果にかかわらず失効を試み、成否を監査記録に残す。発行応答の照合に失敗した場合も、取得に使わずに失効を試みる

GitHub App には、適用するデプロイで `Single file` を `Read-only` で付与し、パスは GATES が固定したパスだけにします。
`Read and write` にしないのは、`single_file:write` のトークンでリポジトリポリシーを書き換えられ得るためです（書き込めるかは公式資料にない。[GitHub App Constraints](../external/github/app.md) §4.5）。
`Contents` の `read` でリポジトリポリシーを読む方式は採りません。
GitHub App に付与した権限は署名能力の悪用で得られるため（§5.1）、読める範囲が Installation の全リポジトリの内容に広がるためです。

リポジトリポリシーによる拒否と取得の失敗は、既存の失敗の種別に当てはめ、種別とエラーコードを増やしません（[Domain Model](domain.md) の Failure Kinds）。
応答の `message` は、エラーコードごとの固定の文言のままにします。
リポジトリポリシーの内容（許可 Caller の ID と名前、権限の上限）は応答に出しません。
応答に出すと、要求できる Caller を探る手がかりを、許可されない呼び出し元にも与えるためです。
監査記録に残す拒否の理由と、内容を記録しないことは §5 に定めます。

リポジトリポリシーについて、次のリスクを受容します。

- **書き込める主体による変更**：対象の既定ブランチに書き込める主体は、Admin でなくても、リポジトリポリシーを書き換えられる。固定のパスにシンボリックリンクを置くと、リンク先がファイルであれば、GitHub はリンク先の内容を通常のファイルと見分けられない形で返すため（[GitHub App Constraints](../external/github/app.md) §4.5）、リンク先を書き換えられる主体もリポジトリポリシーを変えられる。シンボリックリンクを置けるのは固定のパスに書き込める主体だけで、リポジトリポリシーを決められる主体の範囲は、その主体がリンク先を選ぶことで決めた範囲を超えない
- **書き込みのトークンによる書き換え**：リポジトリポリシーで `contents:write` を許された Caller は、そのトークンで対象のリポジトリポリシーを書き換え（`contents:write` で固定のパスを書き換えられることは同 §4.5）、自分に別の権限を許せる。そのため、ある Caller に `contents:write` を許すことは、発行上限と GitHub App の権限の範囲で、その対象へのすべての権限を許すことに等しい。`administration:write` は、コラボレーターやデプロイキーを加えて既定ブランチへの書き込みを得られ、ブランチ保護も外せるため（§3.5）、同じ扱いになる。この書き換えで越えさせたくない上限は、保護対象の一覧で決める（§3.6）
- **Caller の粒度**：Caller はリポジトリ単位のままである。許可 Caller のリポジトリでワークフローを動かせる者は、その許可 Caller に許した範囲を使える
- **認可の前に取得するトークン**：ポリシー読み取りトークンは GATES の外に出さないが、Lambda の侵害、失効の失敗、中断で、GitHub の有効期限まで GitHub 側に残り得る。失効が `204` を返した後も、短い間使えた事例がある（同 §4.3）。読める範囲が、固定のパスのファイル、そこに置いたシンボリックリンクのリンク先、Installation の対象外の公開リポジトリのファイルに限られることは観測だけによる（同 §4.5）
- **取得と発行の間の変更**：発行処理がリポジトリポリシーを読んだ後の変更は、その発行処理に反映されない。発行済みのトークンも失効しない
- **名前による取得**：上に述べた、取得の間に名前が別のリポジトリを指す競合である。得られる許可が、リポジトリポリシーを書き換えられる主体の範囲を超えないため受容する
- **公開範囲**：リポジトリポリシーは、対象のリポジトリを読める主体が読める。資格情報ではないが、許可 Caller を経由した到達（§3.6）の標的を選ぶ手がかりになる
- **複製による引き継ぎ**：リポジトリポリシーは対象の Repository ID も名前も持たない。そのため、テンプレートからの生成などで既定ブランチの内容を複製してリポジトリを作り、複製した内容に固定のパスのファイルが含まれると、作ったリポジトリは作った時点から複製元と同じ Caller と権限を許す。複製した主体は作ったリポジトリに書き込めてリポジトリポリシーも書き換えられるため、許可を決める主体の範囲は変わらない。複製したリポジトリポリシーを残すかは、作ったリポジトリの管理者が確かめる
- **リポジトリの存在の判別**：ポリシー読み取りトークンは §3.1 の条件 5 を判定する前に発行するため、どのリポジトリポリシーにも許されていない Caller も、要求した名前が Installation に含まれない場合（GitHub 発行拒否）と、含まれてリポジトリポリシーで拒否される場合（認可拒否）を、エラーコードで見分けられる。得られるのは Installation に含まれるリポジトリの名前があるかどうかだけで、リポジトリポリシーの内容もトークンも得られず、要求できるのは許可オーナーのワークフローに限られる（§3.1 の条件 1）ため受容する
- **導入の順序**：適用に切り替えた時点で、リポジトリポリシーのない対象への発行が止まる。運用者は、切り替えの前に各対象にファイルを置くよう周知する。拒否せず記録だけする動作は設けない。適用の有無で判定が分かれる動作を増やすと、試験する組み合わせと、記録だけのまま運用される誤りが増えるためである
- **適用しないデプロイ**：§3.5 のリスクがそのまま残る

## 4. Secret and Token Lifecycle

GitHub App Private Key の鍵素材は、Terraform の State / Plan と Go アプリケーションに渡しません。

| 資格情報 | 保存・利用の境界 |
|---|---|
| GitHub App Private Key | KMS インポート前は運用者が別の運用境界で扱う。Lambda と Runner には渡さない。インポート後、インポート前のコピーは運用者の手元から削除する。KMS にインポートした鍵素材は取り出せないため、KMS Key を失った場合は GitHub 側で新しい秘密鍵を発行して切り替える |
| AWS KMS Key | インポート済みの非対称署名鍵。Lambda 実行 Role に当該キーの `kms:Sign` のみ許可。鍵更新時は新 KMS Key を用意し、Lambda が参照する鍵（使用中の鍵）を切り替える。切り替えの確認の後に旧 KMS Key を無効にし、GitHub 側で旧 Private Key を削除した後に、旧 KMS Key を Terraform の管理から外して削除を予約する |
| GitHub App JWT | KMS 署名で Lambda が短時間生成し、GitHub API 呼び出しにのみ使用。外部返却・ログ出力禁止 |
| ポリシー読み取りトークン | リポジトリポリシーを適用するデプロイで、§3.1 の条件 1 から 4 と Installation の条件が成立した要求に対してだけ、Installation Access Token と同じ発行 API で取得する。権限は `single_file:read`（付随する `metadata:read` を許容）、対象は要求した完全名に限る。Lambda の中でリポジトリポリシーの取得にだけ使い、Runner へ返さず、応答、ログ、監査記録に書かない。取得の後、取得の成否にかかわらず失効を試み、成否を監査記録に残す。中断した場合は失効を試みられず、有効期限まで残り得る（§3.7） |
| Installation Access Token | 要求・認可された対象と Permissions（付随する `metadata:read` を許容）に限定して Runner へ返す。短命でも窃取リスクは残る。照合に失敗したものは返さず、文字列を取得できた場合に失効を試みる。Runner へ返したものは、ジョブの終了時の失効と失敗時の失効で、Docker Action が失効を試みる。Runner の上では、Runner のファイルコマンドのディレクトリにある Output と `GITHUB_STATE` のファイルにだけ書く |
| AWS 一時認証情報・AWS 用 OIDC JWT・GATES 用 OIDC JWT | Runner の上で Docker Action の子のプロセスのメモリの中だけで扱い、ファイル、環境変数、Output に書かない。プロセスの終了とともに手放す。ログやデバッグ出力に含めない |

## 5. Failure, Audit, and Security Risks

失敗は次のように扱います。

- 入力が不正、または認証に失敗したら、GitHub API や KMS のトークン発行処理に進まない。Installation の解決や署名の失敗、発行結果の不一致は Fail Closed とする。
- 初期化の失敗（固定設定の欠落か不正、AWS SDK の設定の読み込みの失敗）のログには、満たさなかった条件と、どの値の条件かだけを書き、値を書かない。GATES 用 Audience と KMS Key ARN は資格情報ではないが、ログに書く値を増やさない。
- Handler が回復した panic の値は、応答、監査記録、ログのどれにも書かない。値に資格情報が入っていない保証がないためである。
- 相関 ID は成功応答と失敗応答の両方に、同じ位置で含める。ワークフローのログに残った相関 ID から監査記録へたどれるようにするためである。

監査記録の項目と記録する条件は [Domain Model](domain.md#audit-record) に定め、本節は記録する値と記録しない値を定めます。

- 時刻と結果（成功またはエラーコード）は常に記録する。秘密鍵、OIDC JWT、GitHub App JWT、Installation Access Token、ポリシー読み取りトークン、AWS 一時認証情報は記録しない。
- ポリシー読み取りトークンの失効の結果は、利用者に返すトークンの照合失敗で試みる失効の結果とは別の項目として記録する。ポリシー読み取りトークンは利用者に返さないため、GATES の外で失効を試みる主体がおらず、GitHub 側に残り得るかを調べる手がかりがこの記録だけになるためである。
- リポジトリポリシーの内容（許可 Caller の ID と名前、権限の上限）は記録しない。拒否の理由には、どの対象のリポジトリポリシーが、ない、不正、許していないのどれだったかだけを残す（§3.7）。
- 認証前の失敗では Caller が確定していないため、未検証の値を認証済み主体として記録しない。
- ワークフロー実行 ID と試行番号は、監査記録から GitHub 上のワークフロー実行にたどり着くために残し、認可には使わない。
- ワークフロー起動属性（`actor`、`event_name`、`ref`、`workflow_ref`、`environment` など）は、後述の `pull_request_target` の悪用のように、どのイベントと ref でトークンを得たかを調べる場面に備えて残す。GitHub 側の記録は保持期間を過ぎたり削除されたりし得るためである。ベストエフォートで記録し、Claim が欠落していても拒否しない。
- 署名検証済みの Claims Set は、JWT の文字列ではなく Claims Set の JSON オブジェクトだけを残す。JWT の文字列は有効期限内は Bearer の資格情報であり、署名を検証する前の Payload は攻撃者が内容と大きさを自由に作れるためである。利用者が選んだ文字列を含む Claim も値ごとに検査せず、JSON として再符号化するときのエスケープに任せる。監査記録にだけ書き、Caller への応答やワークフローのログには出さない。パブリックリポジトリでは GitHub 側のログを誰でも読めるためである。
- IAM Role の引き受けと Lambda の呼び出しは AWS 側の記録（CloudTrail）が担い、GATES の監査記録はそれを補うアプリケーション層の記録と位置づける。引き受けは管理イベントとして拒否も既定で残るが、Lambda の呼び出しはデータイベントで、その記録を有効にしていない場合は成功も拒否も残らない（[AWS Lambda Invoke Rejection](../research/aws/lambda-invoke-rejection.md#cloudtrail)、[AWS STS Legacy Subject](../research/aws/sts-legacy-subject.md#cloudtrail)）。成功した引き受けの記録には、発行された AWS 一時認証情報の `accessKeyId` と `sessionToken` が残る（`secretAccessKey` は残らない）。

次のリスクを受容します。

- **ワークフロー内の信頼できないコード**：許可オーナー配下のリポジトリであることは、ワークフロー内のコードの信頼性を保証しない。`pull_request_target` と `workflow_run` のジョブは、base のリポジトリの既定のブランチのワークフローで動き、fork からの Pull Request が起点でもトークンを得られる見込みである（[GitHub Workflow Event Contexts](../research/github/workflow-event-contexts.md)）。そのジョブが Pull Request のコードや起点のワークフローの成果物を実行すると、そのコードがトークンを得る。`pull_request_target` の `sub` は `pull_request` と同じ形のため、Trust Policy ではこの 2 つを区別できず、GATES もイベントの種別で拒否しない。利用者は資格情報を取得するジョブで信頼できないコードを実行しない
- **`pull_request_target` と `workflow_run` の起点の追跡**：これらの監査記録の `ref` と `sha` は既定のブランチの値で、署名検証済みの Claims Set からも起点の Pull Request やワークフロー実行を一意に特定できるとは限らない。起点は、ワークフロー実行 ID から GitHub をたどって調べ、GitHub 側の記録の保持期間を過ぎると調べられない
- **資格情報の漏えいと再利用**：JWT、AWS 認証情報、Installation Access Token の漏えい・再利用を完全には防止しない。許可範囲、期限、権限とインストール対象の限定で影響を抑える
- **Docker Action のコンテナが持つ権限**：Docker Action のコンテナは root で動き、Runner は Docker ソケットと、同じジョブのほかのステップと共有する `RUNNER_TEMP` と `HOME` をマウントし、`ACTIONS_RUNTIME_TOKEN` と要求用トークンを渡す（[GitHub Actions Integration Constraints](../external/github/actions.md)）。コンテナの中のコードは、ソケットを通じて Runner のホストの root に相当する権限を得られ、ジョブのランタイムを操作するトークンも持つ。どれも Runner が決め、Docker Action からは外せず、同じジョブの `run` のステップもパスワードなしの `sudo` と同じ値の要求用トークンを持つため、Docker Action のコンテナに固有の権限ではない。Docker Action のプログラムはソケットと `ACTIONS_RUNTIME_TOKEN` を使わないため、このリスクが現れるのは、プログラム、その依存、ビルド用のイメージが改ざんされた場合である。依存とビルド用のイメージをバージョンと digest で固定し、利用者が Docker Action を commit SHA で参照することで、改ざんされたものが取り込まれる機会を抑える
- **同じジョブのほかのステップからの読み取り**：Docker Action が Runner の上に書く資格情報は、Output と `GITHUB_STATE` のファイルの中のトークンだけである（[GitHub Docker Action Runtime](../research/github/docker-action-runtime.md#files-left-by-the-gates-action)）。Runner はファイルコマンドのファイルをステップの後も消さず、前のステップが起動したバックグラウンドのプロセスはステップをまたいで動き続けるため（[GitHub Actions Integration Constraints](../external/github/actions.md)）、トークンを同じジョブのほかのステップから隠すことはできない。資格情報を守る境界はジョブであり、資格情報を取得するジョブで信頼できないコードを実行しない前提（前述）で受容する
- **失効の取りこぼし**：ジョブの終了時の失効と失敗時の失効はベストエフォートであり、失効の要求が失敗した場合と、Runner がコンテナを強制終了するか Runner が停止して失効を試みる前に Docker Action が終わった場合に、Runner へ返したトークンが GitHub 側の有効期限まで有効なまま残る。残ったトークンの範囲は要求した対象と Permissions に限られ、読み取り以外の権限を要求していれば、その操作ができる。失効の要求が `204` を返した後も、短い間はトークンが使えることがある（[GitHub App Constraints](../external/github/app.md)）。その間にトークンを使えるのは、失効の前からトークンを読める同じジョブのステップとプロセスだけである
- **取り下げた Issuer の鍵による検証**：保持した Issuer の公開鍵に有効期限を設けないため、Issuer が JWKS から鍵を取り下げても、JWKS の再取得に成功するか実行環境が入れ替わるまで、取り下げた鍵で検証できる JWT を受理し続ける。Lambda は実行環境を数時間ごとに終了する見込みだが、AWS は正確な間隔を公開しておらず、GATES はこの期間の上限を保証しない。新しい JWT を偽造するには取り下げた鍵の秘密鍵が要るが、取り下げ前に発行された JWT の再提示には要らず、その `exp` までは受理され得る。どちらの悪用にも、Lambda の Invoke を許可された IAM 認証情報が別に必要である。期限を設けると、期限切れのたびに取得が発生し、Issuer の障害で正当な JWT まで拒否し得るため、この可用性の低下を避ける。Issuer の鍵の漏えいが判明したときは、運用者が関数のコードか設定を更新し、保持した鍵を持たない実行環境に入れ替える（更新の後の呼び出しが新しい実行環境で動くことは、AWS の定めからの推論と [AWS Fault Injection](../research/aws/fault-injection.md) の観測による）
- **GitHub API の呼び出しの増加**：リポジトリポリシーを適用するデプロイでは、1 回の発行処理の GitHub API の呼び出しが、ポリシー読み取りトークンの発行と失効、対象ごとのリポジトリポリシーの取得の分だけ増える。Installation Access Token による呼び出しは Installation のレート制限に数えられ（[GitHub App Constraints](../external/github/app.md) §4.1）、許可オーナーのワークフローは、事前認可を通り、リポジトリポリシーで拒否される要求を繰り返すことで、このレート制限を消費させ、ほかのワークフローの発行を止め得る。影響は可用性にとどまり、GATES はトークンを返さない。連続した要求の制限は [Scope](../spec/scope.md) の将来の機能である
- **Discovery と JWKS の取得の誘発**：再取得の上限は実行環境ごとで、関数全体の上限を設けない。IAM の認可を得た呼び出し元は、手元の鍵で検証できない JWT を送ることで、実行環境ごとに、再取得の上限が許す頻度まで取得を起こせる。署名の検証には鍵が要るため、取得の前に不正な JWT を見分けることはできない。Issuer がレート制限を返すと、鍵を持たない実行環境とローテーション後の鍵を要する JWT は、再試行できる失敗で拒否され続け得る（Issuer のレート制限の有無は未確認）。影響は可用性にとどまり、GATES はトークンを返さない。実行環境をまたいで上限を共有すると、そのためだけに外部の状態、権限、障害の経路が増えるため採らない。同時に動く実行環境の数は Reserved Concurrency で抑えられるが、新しい実行環境は取得の履歴を持たないため、厳密な上限にはならない

### 5.1 KMS Signing Key Risks

KMS Key の署名能力は、GitHub App として認証する手段そのものです。
そのため、Key Policy と IAM で抑える範囲と、それでは抑えられずに受容する範囲を分けて定めます。

次のリスクは、設定で抑えます。

| リスク | 抑える手段 |
|---|---|
| 秘密鍵の取り出し | KMS にインポートした鍵素材は取り出せない。Terraform の State / Plan、Git、CI の成果物、Lambda の環境変数に鍵素材を渡さない |
| 実行 Role による鍵の管理 | 実行 Role に許可する KMS の操作を `kms:Sign` だけにする |
| 実行 Role による別の方式での署名 | Key Policy で署名アルゴリズムを `RSASSA_PKCS1_V1_5_SHA_256` に限る |
| 実行 Role による別の鍵での署名 | 実行 Role の IAM ポリシーに使用中の鍵のほかの許可を含めず、GATES の鍵の集合（新旧の 2 つまで）のほかの鍵の Key Policy に実行 Role を書かない |
| IAM の管理権限を持つ主体による直接の署名 | Key Policy で root に許可する操作を列挙し、`kms:Sign`、`kms:*`、`kms:CreateGrant` を含めない |
| Terraform の操作による鍵の削除と置換 | `prevent_destroy` で該当する Plan を拒否する。鍵の集合から鍵を除いた Plan も拒否する |
| 予約した削除の実行 | Terraform が管理する鍵の削除の予約期間（`deletion_window_in_days`）を 30 日にし、その間は `kms:CancelKeyDeletion` で取り消せるようにする |
| CI からの権限の変更 | Terraform を運用者の手元から適用し、CI に適用権限を与えない |

これらの設定は「鍵を管理できる主体は署名できない」を意味しません。
保証するのは、実行 Role 以外の主体が署名するには、Key Policy、Lambda、実行 Role の Trust Policy のいずれかの変更か、実行 Role を別の関数に渡す操作が別に必要になるところまでです。

次のリスクは受容します。

- **実行 Role の侵害**：Lambda のコードの脆弱性などで実行 Role の権限を奪われると、`kms:Sign` で不正に署名できる。KMS は秘密鍵の取り出しを防ぐが、署名能力の悪用は防がない
- **`kms:PutKeyPolicy` を持つ主体**：Key Policy を書き換えて、自身に署名を許可できる。`kms:CreateGrant` を一時的に許可して作った Grant は、Key Policy を元に戻しても残る。この Grant を確認して取り消せるように、root に `kms:ListGrants` と `kms:RevokeGrant` を許可する
- **Lambda の更新権限を持つ主体**：関数のコードや設定を変更して、実行 Role の権限で署名させられる。`iam:PassRole` を持つ主体は、実行 Role を別の関数に渡して同じことができる
- **`iam:UpdateAssumeRolePolicy` を持つ主体**：実行 Role の Trust Policy を書き換えて Role を引き受け、署名できる
- **Permissions Boundary を通る別の鍵での署名**：Boundary は同じアカウントとリージョンの KMS Key のうち、鍵素材をインポートした鍵への `RSASSA_PKCS1_V1_5_SHA_256` の `kms:Sign` を許可する。GitHub Actions が引き受ける IAM Role と Lambda 実行 Role のどちらかが、この条件に合う別の鍵で署名できる経路は 2 つある。Role に `kms:Sign` を許可するポリシーが追加され、その鍵の Key Policy が IAM ポリシーへ委任している経路と、その鍵の Key Policy が Role を Principal として直接許可する経路である。後者は Role 側のポリシーが変わらない。GATES の署名鍵は Key Policy が root に `kms:Sign` を許可しないため、前者の経路では署名できない。Boundary を GATES の署名鍵に絞ると Terraform の依存が循環するため、この範囲を受容する
- **適用とインポートを同じ主体が担う構成**：Key Policy は鍵素材のインポートを許可する主体を区別しない。鍵素材のインポートの権限を通常の Terraform 適用から分離することは IAM の権限の割り当てに依存し、Key Policy では保証しない
- **インポート前の秘密鍵のコピー**：運用者の手元のコピーを削除することは手順で定めるだけで、設定では強制できない
- **鍵の更新の間の、使用中でない鍵での署名**：鍵の更新の間は、新旧どちらの鍵の Key Policy も実行 Role に `kms:Sign` を許可するため、実行 Role は使用中でない鍵でも署名できる。使用中でない鍵の Key Policy から実行 Role を外さないのは、外すと切り替えと切り戻しのたびに 2 つの Key Policy を書き換えることになり、上記の `kms:PutKeyPolicy` のリスクを持つ操作が増えるためである。2 つの鍵はどちらも同じ GitHub App の Private Key であり、実行 Role が侵害されたときに得られる能力（GitHub App としての認証）は 1 つの鍵のときと変わらない。新しい鍵は鍵素材のインポートまで署名できない。旧鍵は、切り替えの後の発行を確かめてから運用者が無効にし、この期間を短くする。GitHub 側で旧 Private Key を削除した後は、旧鍵での署名は GitHub に受理されない見込みである（削除した鍵の JWT を GitHub が拒否することは、公式資料からの推論で、GATES を通しては確かめられない）
- **Terraform の管理から外した旧鍵**：退役させる鍵を State から外すと、その鍵の Key Policy と状態は Terraform の Plan に現れなくなる。外す前に鍵を無効にし、外した後は削除を予約する手順で、残る期間をその予約期間（7 日）に限る。この予約期間のあいだは `kms:EnableKey` と `kms:CancelKeyDeletion` を持つ主体が鍵を戻せるが、GitHub 側で Private Key を削除した後のため、戻した鍵で署名しても GitHub App として認証できない見込みである
- **Terraform の設定の除去による鍵の削除**：`prevent_destroy` はリソースの設定自体を取り除いた場合の削除を防がない。Plan に現れた鍵の削除を運用者が確認して止める
- **KMS の API からの鍵の無効化と削除の予約**：`kms:DisableKey` や `kms:ScheduleKeyDeletion` を IAM で許可された主体は、Terraform を経ずに実行できる。`prevent_destroy` は効かず、Terraform は鍵の有効と無効を設定に書かないため、無効化は Plan にも現れない（[AWS Fault Injection](../research/aws/fault-injection.md)）。Lambda は署名できなくなってトークンを発行できない。影響は可用性にとどまる。鍵の悪用が判明したときに一時的に止める手段でもあるため、Key Policy から外さない

`kms:PutKeyPolicy`、Lambda の更新権限、`iam:UpdateAssumeRolePolicy` によるリスクを受容するのは、これらが Terraform の適用に必要な権限と重なり、Key Policy の記述では取り除けないためです。
`kms:PutKeyPolicy` を Key Policy から外すと Terraform で Key Policy を更新できなくなり、署名を拒否する `Deny` を加えても同じ権限で消せます。
これらの権限を持つ主体は、実行主体の限定と変更レビューで制御します。

不正に署名されると、GATES の認可を経ずに GitHub App JWT を作れるため、§3.1 と §3.3 の制限（発行上限、保護対象の一覧、リポジトリポリシーを含む）は効きません。
得られるトークンの上限は、GitHub App の権限と Installation の対象で決まります。
リポジトリポリシーを適用するデプロイで GitHub App に付与する `single_file:read` もこの上限に含まれ、Installation の全リポジトリのリポジトリポリシーを読めます。
この権限で読める範囲は、`Contents` の `read` を付与した場合と異なり、固定のパスのファイル、そこに置いたシンボリックリンクのリンク先、Installation の対象外の公開リポジトリのファイルにとどまります（観測による。[GitHub App Constraints](../external/github/app.md) §4.5）。
リポジトリポリシーは資格情報ではなく、もともと対象のリポジトリを読める主体には読めるものです（§3.7）。
GATES が発行しない Organization permissions と Enterprise permissions も、GitHub App に付与され、GitHub App が Organization か Enterprise にインストールされていれば、この上限に含まれます。
Account permissions は、GitHub App JWT から得られる Installation Access Token には付かず、署名能力の悪用だけでは得られないと推論されます（[GitHub App Constraints](../external/github/app.md)）。
GitHub App に付与する権限を広げるほど、署名能力の悪用で得られる権限も広がります。
GATES は不正な変更や署名を通知する仕組みを持たないため、悪用に気付くまでの時間は保証できません。
悪用が判明したときは、GitHub 側で Private Key を失効させて止めます。
`kms:DisableKey` による停止は `kms:EnableKey` を持つ主体が元に戻せるため、これだけでは確実に止められません。
`kms:DeleteImportedKeyMaterial` は Key Policy に含めません。
インポート前のコピーは削除する運用のため、鍵素材を消すと同じ鍵には戻せず、悪用を止める目的には GitHub 側の失効で足りるからです。

## Appendix: Impact of Future Scope

[Scope](../spec/scope.md) が将来取り込むことを想定する機能を導入する場合、本ドキュメントには次の影響が及びます。

- **細粒度の認可の残る部分**：チームに応じて制御するなら、リポジトリポリシーを変更できる主体を GitHub の権限（Team への権限の付与を含む）に委ねている現在の形で何が足りないかと、GATES が User と Team の名簿を持つことの脅威を評価する。監査のためだけに用いているワークフロー起動属性を認可に使って Caller をリポジトリより細かく見分けるなら、属性の値を変えられる主体と、認可の根拠にできるかを評価する。許可 Caller に条件を加える形にするなら、リポジトリポリシーを書き換えられる主体がその条件も決めることになる（§3.7）
- **Organization permissions、Account permissions、Enterprise permissions の発行**：認可条件 3、権限の境界、発行結果の照合が変わる。リポジトリを単位とする認可条件と照合をそのまま一般化しない。Account permissions は Installation Access Token に付かないため、発行するにはユーザーアクセストークンを扱う必要がある。ユーザーアクセストークンは本人のブラウザ操作で得て、リフレッシュトークン（有効期限 6 か月）で取り直すため、長期の資格情報を GATES の側で保管することになり、資格情報の扱いから見直す
- **OIDC JWT の再利用の検出とレート制限**：受容している JWT の再利用のリスクを見直す。どちらも実行環境をまたいで要求の履歴を共有する必要があり、再取得の上限の共有を採らない理由とした外部の状態、権限、障害の経路が増えるため、それらの脅威と、その状態に障害が起きたときに Fail Closed とするかを評価する

スコープを変更するときは、先に本ドキュメントで脅威と緩和策を評価し、その結果を踏まえて [Requirements](../spec/requirements.md) と各設計書を変更します。
