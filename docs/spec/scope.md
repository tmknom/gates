# Scope

## 1. Purpose

本ドキュメントは、GATES の現在のスコープ、将来取り込むことを想定している機能、対象外とする範囲を示します。
GATES が満たす要求は [Requirements](requirements.md) に定めるため、本ドキュメントを更新しただけでは GATES への要求は変わりません。

## 2. Current Scope

許可された単一のオーナー配下のワークフローが、Installation に含まれるリポジトリを、GitHub App に付与され、発行上限に含まれる Repository permissions の範囲で操作するためのトークンを取得できるところまでを実現します。
**発行上限** は、GATES 運用者がデプロイ時の設定で定める、そのデプロイで発行してよい権限の範囲です（[Requirements](requirements.md) の FR-AUTHZ-008）。
**保護対象の一覧** は、GATES 運用者がデプロイ時の設定で定める、要求できる Caller と権限を限るリポジトリの集合です（[Requirements](requirements.md) の FR-AUTHZ-009）。
**リポジトリポリシー** は、アクセスされる側のリポジトリが自分の中に置く、自分への要求を許す Caller と権限を定めたファイルです（[Requirements](requirements.md) の FR-AUTHZ-011）。
GATES 運用者は、リポジトリポリシーを適用するかしないかをデプロイごとに決めます。
次の表の項目は、恒久的な原則ではなく、現在の選択です。

| 項目 | 現在のスコープ | 理由 |
|---|---|---|
| **認可の粒度** | オーナー単位で認可し、Caller はリポジトリ単位で見分ける。発行上限はデプロイに一つで、どの Caller にも対象リポジトリにも同じに効く。保護対象の一覧に指定したリポジトリへの要求は、許可 Caller と権限の上限で制限する（[Requirements](requirements.md) の FR-AUTHZ-009）。リポジトリポリシーを適用するデプロイでは、すべての対象への要求を、その対象のリポジトリポリシーが許す Caller と権限に限り、有効なリポジトリポリシーのない対象への要求を拒否する（[Requirements](requirements.md) の FR-AUTHZ-011）。適用しないデプロイでは、保護対象の一覧にないリポジトリは、Caller ごとに制限しない | 操作できるワークフローを一部のリポジトリのものに限りたいリポジトリを、Installation に含めたまま守るため。リポジトリポリシーを適用すれば、中央の一つの設定の大きさの上限に縛られずに、守る範囲をすべてのリポジトリに広げ、新しいリポジトリを既定で拒否できる（リポジトリポリシーを持つリポジトリの内容を複製して作った場合を除く。[Security Design](../design/security.md) §3.7）。適用を選べるようにするのは、適用すると GitHub App の権限の追加と、各リポジトリへのファイルの配置が要るため |
| **発行可能な権限** | Repository permissions を許可する（[Requirements](requirements.md) の FR-AUTHZ-006）。そのうち発行するのは、発行上限に含まれるものに限る。Organization permissions、Account permissions、Enterprise permissions は発行しない | リポジトリを横断する自動化には、読み取り以外の権限も要るため。リポジトリを単位としない権限は、対象リポジトリの明示では影響範囲を限定できないため発行しない |

GATES が発行するトークンの対象と権限の範囲を決めるのは、GitHub App に付与する権限、Installation の対象、発行上限、保護対象の一覧、リポジトリポリシーです。
GitHub App の権限と Installation の対象は GitHub 側の設定（GitHub App / オーナーの管理者の責任）、発行上限と保護対象の一覧は GATES のデプロイ時の設定（GATES 運用者の責任）、リポジトリポリシーはアクセスされる側のリポジトリの中のファイル（そのリポジトリの管理者の責任）です。
どれも条件を加えるだけで、ほかの条件で拒否される要求を許可に変えません。
発行上限は、どのワークフローに対しても同じ範囲を狭めるだけで、オーナー内の横断的な操作そのものは防ぎません。
保護対象の一覧は、指定したリポジトリへの要求を、**許可 Caller**（要求を許す Caller のリポジトリと権限の上限の組）に当たる Caller からの、その権限の上限の範囲の要求に限ります。
リポジトリポリシーも、許可 Caller を同じ形で定めます。

リポジトリポリシーを適用しないデプロイでは、許可オーナーのどのワークフローも、Installation に含まれ、保護対象の一覧にないどのリポジトリ（新しく作ったリポジトリを含む）に対しても、GitHub App に付与され、発行上限に含まれる Repository permissions のすべてを要求できます。
保護対象の一覧にないリポジトリは、そのリポジトリに対する操作を GATES の認可では制限できません。

リポジトリポリシーを適用するデプロイでは、この横断的な操作は、各リポジトリのリポジトリポリシーが許した Caller と権限に限られます。
一方で、リポジトリポリシーを変更できる主体は、GATES ではなく GitHub の権限で決まります。
対象のリポジトリの既定ブランチに書き込める主体は、リポジトリの管理者でなくても、リポジトリポリシーを書き換えられます。
リポジトリポリシーで書き込みの権限を許された Caller も、発行されたトークンでリポジトリポリシーを書き換え、自分に別の権限を許せます。
保護対象については、保護対象の一覧が、この書き換えでも越えられない上限として残ります。

どちらのデプロイでも、許可 Caller のリポジトリのワークフローを書き換えられる者は、その許可 Caller として、権限の上限の範囲で要求できます。
この経路、リポジトリポリシーを適用しないデプロイでの保護対象の一覧にないリポジトリへのオーナー内の横断的な操作、リポジトリポリシーの書き換えを、現在のスコープに伴う残留リスクとして受容します。
恒久的に受け入れたものではなく、細粒度の認可の残る部分を取り込むときに見直します。

## 3. Deferred Capabilities

次の機能は現在のスコープに含めず、将来取り込むことを想定します。
優先順位と実施時期は未定です。

| 項目 | 想定する拡張 |
|---|---|
| **細粒度の認可** | 保護対象の一覧とリポジトリポリシーで制限する範囲を超えて、認可を制御する。チームに応じて制御すること、Caller をリポジトリより細かく（ブランチ、イベント、Environment、ワークフロー）見分けることを含む |
| **Organization permissions、Account permissions、Enterprise permissions の発行** | リポジトリを単位としない権限を発行できるようにする |
| **OIDC JWT の再利用の検出** | 有効期限内に同じ OIDC JWT を使った要求を検出する。現在は、再利用できる期間を [Requirements](requirements.md) の FR-AUTHN-001 の時間条件だけで制限している |
| **レート制限と濫用の検出** | 連続した要求を制限し、濫用を検出する |
| **カスタマイズした `sub` の受理** | `include_claim_keys` でカスタマイズした `sub` の GATES 用 OIDC JWT を受理する。現在は、`repo` の部分で始まり、その後に `:` が続く形式だけを受理する。IAM Role の引き受けも `sub` の先頭が許可オーナーの不変 Owner ID を示すことを求めるため（[Requirements](requirements.md) の FR-AUTHN-003）、`repo` の部分で始まらない形式に広げるときは、引き受けの条件もあわせて検討する |

Organization permissions、Account permissions、Enterprise permissions は、Repository permissions と影響範囲が異なり、対象リポジトリを明示しても範囲が狭まらないため、Repository permissions と同じ認可で扱えるとは仮定しません。
これらを発行するときは、現在のオーナー単位の認可のまま広げず、認可の粒度と一体として検討します。

細粒度の認可の残る部分は、リポジトリポリシーを変更できる主体を GitHub の権限で絞るだけでは、互いに信頼できないチームを分けられなくなったときや、許可 Caller のリポジトリでワークフローを動かせる者の範囲が、許可したい範囲より広いときに検討を始めることを想定しています。

## 4. Out of Scope

次の範囲は GATES の対象外とし、将来の導入も想定しません。

- 複数のオーナーの同時サポート
- 複数の GitHub App Installation の同時サポート
- GitHub Enterprise Server など GitHub.com 以外の GitHub への対応
- IAM 層で拒否された呼び出し（[Requirements](requirements.md) の FR-OPS-002）の監査記録。記録されるかどうかは AWS の仕様に依存し、GATES は保証しない
