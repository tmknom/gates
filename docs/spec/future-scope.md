# Future Scope

## 1. Purpose

本ドキュメントは、GATES の現在のスコープから外しているものの、将来取り込むことを想定している機能を示します。
現在必ず満たす要求と受け入れ条件は [Requirements](requirements.md) に定めるため、本ドキュメントを更新しただけでは GATES への要求は変わりません。

## 2. Current Scope

現在は、GATES の E2E の成立を優先する段階です。
許可された単一のオーナー配下のワークフローが、Installation に含まれるリポジトリを読み取るためのトークンを取得できるところまでを実現します。
次の表の項目は、恒久的な原則ではなく、この段階の選択です。

| 項目 | 現在のスコープ | 理由 |
|---|---|---|
| **認可の粒度** | オーナー単位で認可する。Caller やチームごとにアクセス先を制限しない | 認可ポリシーの管理と運用を増やさず、E2E の成立を優先するため |
| **発行可能な権限** | `contents:read` のみ許可する | オーナー内の横断的なアクセスが残る段階で、発行できる権限を読み取りに限定するため |

オーナー内の横断的な読み取り要求は、現在のスコープに伴う残留リスクであり、恒久的に受け入れたものではありません。

## 3. Deferred Capabilities

次の機能は現在のスコープに含めず、将来取り込むことを想定します。
優先順位と実施時期は未定です。

| 項目 | 想定する拡張 |
|---|---|
| **細粒度の認可** | Caller やチーム、アクセス先に応じて認可を制御する |
| **発行可能な権限の拡大** | 追加のリポジトリ権限を発行できるようにする。Account / Organization に関係する権限も候補とする |

権限を広げるほど、オーナー内の横断的なアクセスがもたらす影響も大きくなります。
そのため、現在のオーナー単位の認可のまま権限を広げられるとは仮定せず、認可の粒度と発行可能な権限を一体として検討します。
特に Account / Organization に関係する権限は、リポジトリ権限と影響範囲が異なり得るため、リポジトリ権限と同じ認可で扱えるとは仮定しません。

いずれの拡張も、E2E の検証から実利用へ移るときや、機密性の高いリポジトリを Installation に含めるときに検討を始めることを想定しています。

複数のオーナーや GitHub Enterprise Server への対応など、[Requirements](requirements.md) で対象外とした範囲について、本ドキュメントは将来の導入を想定しません。
