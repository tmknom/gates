# GATES — Project Scope

## 1. Purpose and Responsibility

本ドキュメントは、GATES が**現在どの範囲を実現するか**、どの機能を**意図的に先送りしているか**、その理由と再評価の契機を一元管理します。段階的な開発のための**スコープ判断の正本**とします。

本ドキュメントの Current Scope は、最終的な製品の機能上限や将来のロードマップを意味しません。開発の進展や新たな安全対策の検討を受けて、判断を更新することを想定しています。ただし、**本ドキュメントを更新しただけで GATES の発行許可条件が変わるわけではありません**。

責務は次のように区別します。

| 文書 | 担当する判断・規定 |
|---|---|
| **本ドキュメント** | 現在のスコープ、先送りの理由、将来の再評価方針 |
| [Requirements](requirements.md) | 現在必ず満たす要求、対象外の範囲、受け入れ条件 |
| [Security Design](../design/security.md) | 現在の認証・認可境界、実際に残るリスク、運用上の安全措置 |
| [Domain Model](../design/domain.md) / [Lambda Design](../design/lambda.md) | 現在の認可ルール、不変条件、具体的な受理・拒否条件 |
| [GitHub Constraints](github-constraints.md) / [JWT Constraints](jwt-constraints.md) | GitHub の仕様・標準仕様の根拠と適用条件 |

要件や設計の詳細な検証規則は、本ドキュメントでは重複して定義しません。また、本ドキュメントはリスク評価の代替ではありません。未解消の脅威と緩和策は Security Design で扱います。

## 2. Current Scope

現在は、**GATES の E2E の成立を優先し、認証・認可・発行・返却の最小構成を実現する**段階です。次の二つは、恒久的な原則ではなく、この段階のスコープ判断です。

| 項目 | 現在の選択 | 目的・理由 |
|---|---|---|
| **認可の粒度** | 許可された単一のオーナー配下のワークフローを、オーナー単位で認可する。Caller／チームごとにアクセス先を制限する認可は設けない | 認可ポリシーの管理基盤と運用を増やさず、E2E の成立を優先する |
| **発行可能な権限** | GATES が受け付ける要求の権限は `contents:read` のみ。他の権限は拒否する | オーナー内の横断認可が残る段階で、発行できる権限を限定する |

この段階でも、利用者に対象リポジトリを明示させ、GitHub App の Installation が許す範囲を超えて発行しないこと、発行結果を照合することなど、既存のセキュリティ要求は維持します。具体的な要求は [Requirements](requirements.md)、技術上のルールは [Security Design](../design/security.md) と [Lambda Design](../design/lambda.md) を正本とします。

**権限には異なる三つの境界があります。** GitHub App / Installation に付与された権限、GATES が要求として許可する権限、実際に返却する Installation Access Token の実効権限は同一とは限りません。現在の GATES の許可条件は `contents:read` のみです。GitHub が要求とは別に付与する `metadata:read` の扱いは、発行結果の照合条件として [Lambda Design](../design/lambda.md) 等で規定します。GitHub App 側も初期段階では `contents:read` に限定する意向ですが、実際の GitHub 側設定は本ドキュメントでは検証していません。App 側だけの権限変更によって GATES 側の許可条件が自動で変わるわけではありません。

**残るセキュリティ上の露出**：オーナー内の横断的なトークン要求は、**現在のスコープ判断に伴う残留リスク**であり、恒久的に全面受容したという判断ではありません。
リスクの分析と運用上の緩和策は [Security Design](../design/security.md#32-installation-scope-as-authorization-boundary) を参照します。

## 3. Deferred Capabilities

次の機能は、**現在のスコープに含めず、後続の検討対象として残す**ものです。採用する方式、優先順位、実施時期、完了条件は未決定です。

| 項目 | 将来の検討方向 | 現時点で決めないこと |
|---|---|---|
| **細粒度の認可** | Caller やチーム、アクセス先に応じた認可制御を検討する | ポリシーの正本、管理者、識別子・照合方式、保存先、変更手順、時期 |
| **発行可能権限の拡大** | 追加のリポジトリ権限、さらに Account / Organization に関係する権限も候補とする | 対象となる具体的な権限、追加順序・時期、共通の権限モデルや API 設計 |

権限を低リスクなものから広げていく方向性はありますが、**リスクの大小や順序を現時点で決定したものではありません**。より強い権限を扱うときに、現在のオーナー単位の認可をそのまま使えるとも仮定しません。特に Account / Organization 権限は、リポジトリ権限とは作用対象や影響範囲が異なり得るため、既存の Repository ベースの認可・照合モデルをそのまま一般化しません。

現在対象外の機能すべてが将来の導入候補というわけではありません。複数オーナー、GitHub Enterprise Server 等の**一般的な非対象範囲は [Requirements](requirements.md) §2.2 を正本**とし、将来導入する意向をここで推定しません。

## 4. Reassessment

現在のスコープの維持・変更は、特に**認可の粒度と発行権限を一体として**再評価します。次は検討を開始する契機であり、機能の自動追加や変更期限を意味しません。

- E2E 検証から実利用へ移行する、または機密性の高いリポジトリを Installation の対象に加えるとき
- GitHub App / Installation の権限や対象リポジトリを拡大するとき
- GATES が発行を許可する権限の追加を検討するとき
- Caller を変更できる主体や Installation の管理主体が変化するとき
- 現在の横断認可による影響範囲が、利用目的や許容できるリスクと合わなくなったとき
- 侵害・漏えい・監査上の発見により、現行の緩和策の妥当性に疑義が生じたとき

スコープ変更を決定する場合は、先に Security Design で脅威と緩和策を評価し、その結果を踏まえて [Requirements](requirements.md) の要件・受け入れ条件と各設計書を変更します。**スコープの更新だけで実装・許可権限を変更してはならない**という運用上の前提を維持します。
